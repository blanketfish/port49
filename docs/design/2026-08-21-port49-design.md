# port49 — Design

**Status:** Draft
**Date:** 2026-08-21
**Language:** Go

---

## 1. Summary

port49 is a TACACS+ server that delivers **certificate-based user identity** to network
devices that will never support certificates themselves.

An engineer authenticates once per day — with a hardware-held certificate (PIV, YubiKey, or
equivalent) or against the organization's existing OIDC provider.
For each device login, a local agent transparently mints a **short-lived, device-bound
token** — single-use for a shell login, reusable within its TTL for an HTTP API such as eAPI
(§17) — and supplies it where the device expects a password. The device
performs an ordinary RFC 8907 TACACS+ exchange and requires no configuration change
beyond pointing at port49.

The user's credential never crosses the device's wire. Only a token derived from it does,
and that token is worthless the instant it is spent.

---

## 2. Problem

TACACS+ remains the standard for network device AAA, and its per-command authorization
and accounting have no real substitute. But the deployed protocol has three problems:

**The transport is weak.** RFC 8907 obfuscation is MD5-based and not a security boundary.
RFC 9887 (2025) replaces it with TLS 1.3 and mutual certificate authentication — but no
mainstream network OS ships a TLS-capable TACACS+ *client*. Server-side support exists;
there is nothing to talk to. Any design that depends on RFC 9887 for identity has its
ship date set by hardware vendors.

**Authentication is still a password.** Even inside a TLS tunnel, RFC 9887 authenticates
the *device* to the server. The human at the CLI still proves identity with a password
carried in an ASCII, PAP, or CHAP exchange. Certificate identity for the *user* is
unsolved.

**Operations do not scale.** Existing implementations are mature and correct but assume a
different era: single-process daemons with local configuration files, bespoke config
languages, and shared secrets that in practice are never rotated — not because operators
choose not to, but because nothing tells them when the old key has stopped being used, so
retiring it is an act of faith. Authorization is
commonly maintained as rendered templates, which do not compose — each new account or
variant requires forking a template, making the platform owner a permanent bottleneck in
a ticket queue.

---

## 3. Goals

- **Strong user identity on unmodified network devices** — hardware-held certificates or
  the organization's existing OIDC provider, neither of which the device ever sees.
- **Standards compliance.** Strict RFC 8907, with RFC 9887 (TLS 1.3) implemented to spec
  for forward compatibility.
- **Declarative, reviewable authorization policy** — composable roles and scopes under
  version control, replacing hand-maintained templates.
- **Machine identity for automation** with no long-lived secret at rest.
- **Horizontal, container-native scaling** with no local state on any replica.
- **Predictable, documented degradation** when dependencies fail.

## 4. Non-goals (v1)

- **SSH certificate authority / device-native SSH cert auth.** A viable complementary
  approach, deliberately deferred. The shared policy core does not preclude it later.
- **RADIUS / RadSec.** Out of scope.
- **Replacing device-local break-glass accounts.** These remain the recovery path of last
  resort and must not depend on port49.
- **General-purpose policy engine.** Policy is scoped to network device AAA.
- **Multi-tenancy.** A deployment serves one fleet, one policy repository, and one directory
  trust domain. Scope and subject names are global within it, `all_devices` spans it, and
  the admission trie is a single address namespace — so tenancy is not a feature that could be
  added later without changing all three. Isolation between tenants is achieved by running
  separate deployments, which is cheap here because the daemon's only hot-path dependency is
  the token store.

---

## 5. Design targets

Stated as requirements, not as observations of any particular environment.

| Target | Value |
|---|---|
| Network devices | 10,000 |
| Sustained authentication rate | ~170/sec (10k devices on a 60s poll interval) |
| Per-command authorization latency | p99 < 5ms, with a warm cache or a same-region store |
| Scaling model | stateless horizontal replicas |
| Directory dependency | must not sit on the authentication hot path |

The sustained rate is driven by high-frequency pollers (metrics collection scripts),
which are the heaviest consumers — far exceeding interactive human logins.

The latency target is qualified deliberately. A cold replica's first command in a login
reaches the store, and under a single global store (§13) that read may cross regions and
consume the whole budget on its own. The target describes steady state.

## 6. Architecture

```
  Engineer laptop                                Network device
  ┌────────────────┐                             ┌──────────────────┐
  │  port49 agent  │                             │  TACACS+ client  │
  │  + credential  │                             │  (unmodified)    │
  └───────┬────────┘                             └────────┬─────────┘
          │ ① authenticate (cert or OIDC), hold session   │ ③ TCP/49 (RFC 8907)
          │ ② mint device-bound token                     │    TCP/300 (RFC 9887)
          ▼                                               ▼
  ┌────────────────────┐   token handle          ┌──────────────────┐
  │      Broker        │ ─────────────────────▶  │      Daemon      │
  │  · validates ident │   (via the operator     │  · TACACS+ proto │
  │  · resolves groups │    or the agent)        │  · redeems token │
  │  · evaluates scope │                         │  · per-cmd policy│
  │  · mints tokens    │                         │                  │
  └─────────┬──────────┘                         └────────┬─────────┘
            │                                             │
            ├──────────────▶ Directory (LDAP/AD)          │
            │                (groups only, cold path)     │
            │                                             │
            ├──────────────▶ Inventory service ◀──────────┤
            │                (snapshot pull, cold path)   │
            ▼                                             ▼
       ┌──────────────────────────────────────────────────────┐
       │                    Token store                        │
       │  · token handles (strong consistency, single-use)     │
       │  · login contexts (eventual, cached at each daemon) │
       └──────────────────────────────────────────────────────┘
```

### Components

Four processes and one dependency. Each is defined as much by what it **must not** do as by
what it does — the prohibitions are what produce the failure behavior in §12, and none of
them is incidental.

| | Speaks | Clients | Never | Scales with | If it dies |
|---|---|---|---|---|---|
| **Agent** | HTTPS out | the operator | holds no policy | operators | that operator's new logins |
| **Broker** | HTTPS | agents, workloads | never speaks TACACS+ | mint rate | new logins only |
| **Daemon** | TACACS+ | network devices | never contacts the directory or a source of truth | devices, live logins | authentication and authorization |
| **Inventory** | HTTPS | broker, daemon | never on a request path | fleet size | nothing, until a device is racked |
| **Token store** | — | broker, daemon | — | logins | everything |

**Agent / CLI (`port49`).** Holds the operator's session, mints tokens on demand, and
integrates at the SSH layer so existing workflows are unchanged. Also provides `login`,
`token`, `explain`, and `test`. Machine workloads do **not** require it — identity is a file
and minting is a single HTTP call.

**Broker.** The only component that talks to the directory. Validates client identity
(certificate, OIDC token, or workload token), resolves group membership, evaluates device
scope, renders platform attributes, compiles the decision, and mints tokens. It never speaks
TACACS+ and never sees a network device.

**Daemon.** Speaks TACACS+. Redeems tokens, evaluates per-command authorization against a
compiled decision, and emits accounting. It never contacts the directory, a source of truth,
or the broker. It is the only component exposed to untrusted binary input, which is why it is
kept a small executor rather than an interpreter of policy.

**Inventory service.** The only component that talks to a source of truth. Runs connectors
(NetBox, Nautobot, and others), applies bounded-change safety, and publishes the inventory as
one signed, versioned bundle document naming the policy it was built against, over a small API
with a read right and a sync right (`POST /v1/sync`). The policy stays local to each port49d,
which joins it to the inventory (policy engine spec §13, decision 29).
Consumers *pull and cache*; nothing queries it per request. It is the one component permitted
to be a singleton, because nothing depends on it being up. It is `port49-inventory` (plan 6b): a
mutual-TLS API with read and sync rights, a signed bundle document kept in its state directory and
written to a shared mirror, and, from plan 6c, the NetBox and Nautobot connectors, whose webhooks
arrive on a TLS listener of their own, authenticated by their signature, and only trigger a sync
(policy engine spec §10).

**Token store.** Holds tokens, receipts, policy blobs, and login contexts, through a narrow
interface (§12). It is the only shared state and the only single point of failure, which is
deliberate: one thing to make reliable rather than four.

### Why these boundaries

**Broker and daemon are split so that a broker failure cannot end an active login.** They
never call each other; the store is the only thing between them. Merged, a slow directory or
a bad policy load during a mint would take per-command authorization down for every operator
mid-session — the worst possible outage shape for network AAA.

**The directory is confined to the broker** because an unreliable or slow directory must not
sit on any hot path, and because it keeps directory credentials in one workload.

**Sources of truth are confined to the inventory service** for the same reason one layer out,
plus two others: connectors are a contributable surface, so running them out of process means
a third-party connector cannot reach the authentication path; and it keeps NetBox credentials
in a single place.

**The singleton is placed where availability does not matter.** The inventory service can be
down for hours; consumers serve the last good bundle. Putting the component that needs no
high-availability story where it costs nothing is a deliberate choice, not an accident — but
it only holds because a daemon can also *start* without it, from a locally persisted bundle
or a shared object-store copy. Otherwise the outage would block autoscaling and crash-loop
recovery, and the singleton would be a startup dependency under another name (policy engine
spec, §10).

**The agent is optional by design.** Anything able to execute a subprocess or make an HTTP
call is a first-class client, which is what keeps the CLI from becoming a gatekeeper (§17).

### Taxonomy

Every named thing in the design, grouped by who creates it and when — which is the question
that actually distinguishes them.

**Authored** — written by operators, reviewed in a pull request, versioned in git.

| Term | Is | Notes |
|---|---|---|
| **role** | a named set of command permits and denies, optionally carrying a privilege level | may carry only rules, only a privilege, or both |
| **scope** | a named selector over device attributes | may match device *state*, so a mitigation lapses as devices are patched |
| **subject** | how policy names a set of principals — an LDAP group, or one or more literal identities | also carries consumer properties: `token_ttl`, `enable`, `username` |
| **grant** | one flat row: subject × scope × roles, with an optional expiry | the unit of access review |
| **privilege level** | an ordered abstract name (`readonly`, `operator`, `admin`) | rendered per platform; never a vendor string in policy |
| **key group** | which CIDR or attribute pattern maps to which key reference | the admission decision; key *material* lives in a secret store |
| **entity class** | a named set of device entity names, referenced as `@class` | shipped per platform, extensible |
| **platform** | a dialect definition: attribute rendering, `supports`, entity classes, normalization parameters | shipped by port49, overridable |

**Imported** — facts about the world, synced rather than authored.

| Term | Is | Notes |
|---|---|---|
| **device** | a NAS record: addresses, platform, attributes | every address it may source from must be listed |
| **bundle** | the inventory, policy and pinned platform set joined as one version; the service publishes the inventory half and each port49d joins its own policy (policy engine spec §13, decision 29) | consumers pull and cache; never queried per request |

**Runtime** — created during execution, never written by hand.

| Term | Is | Lives |
|---|---|---|
| **principal** | the identity that actually authenticated — `CN=alice,…` or a service account | the request |
| **session** | the operator's authenticated state after `port49 login` | 8–16h, in the agent, never sent to a device |
| **login** | one shell session on one device | until the operator disconnects |
| **token** | the short-lived, device-bound secret — single-use, or reusable within its TTL where the subject says so (§17) | store, ≤ `token_ttl`, encrypted at rest |
| **presented credential** | what arrives in the authentication packet — the token for PAP and ASCII, a challenge/response for CHAP | the packet |
| **blob** | the fully compiled decision: rules, pipe allowlist, attributes, normalization parameters. Content-addressed | store, bumped to the longest login context that references it; emitted once into the decision log for replay |
| **receipt** | proof of a completed redemption, bound to the presented credential | store, ~30s |
| **login context** | the daemon's per-login record, keyed `(nas, username)`, holding a blob hash | the login |

**How they compose.** A **principal** matches one or more **subjects**; each **grant** on
those subjects whose **scope** selects this **device** contributes its **roles**; the union
resolves to a **privilege level** and a rule set, which the broker compiles against the
device's **platform** into a **blob**, referenced by a **token**. On redemption the daemon
creates a **login context** pointing at that blob, and every command in that **login** is
answered from it.

Two distinctions carry most of the confusion, so they are worth stating flatly:

> **Principal is runtime; subject is policy.** A principal walks in the door. A subject is how
> policy addresses a set of them.

> **The bundle carries facts; the blob carries decisions.** Facts are needed to accept a
> connection. A decision is needed to authorize a command.

### Key architectural rule

> **The daemon's only hot-path dependency is the token store.**

The broker owns every directory interaction, including background refresh of live session
contexts. The inventory service owns every source-of-truth interaction. This keeps an
unreliable or slow directory entirely off the authentication and authorization hot paths, and
makes the daemon trivially testable with neither a directory nor an inventory present.

The daemon does hold one **cold** dependency: the device admission data, which it needs to
accept a connection at all. It is pulled at startup, refreshed in the background, persisted
locally, and **never expires** — a stale device list is a far smaller problem than no device
list, and an admission table with a TTL would let a prolonged sync outage halt authentication
fleet-wide. Stating this explicitly is better than quietly bending the rule.

That is the daemon's *only* cold dependency, and keeping it that way is why policy and
platform definitions are **compiled into the decision** rather than distributed to daemons
(policy engine spec, §5.1.2). The governing line:

> **The bundle carries facts. The blob carries decisions.**

The daemon needs facts to accept a connection — which device this address is, which shared
key to use. It needs a decision to authorize a command. Because a decision arrives fully
compiled and hash-named, a daemon and a broker can never disagree about how a rule is
evaluated, even mid-upgrade.

## 7. Identity model

### Human identity

Two supported paths, both first class. They differ only in how a human proves identity;
everything downstream is identical.

**X.509 client certificate** presented over mutual TLS to the broker. The private key is
generated on a hardware token — PIV, YubiKey, or equivalent — and never leaves it. The
broker validates the chain, expiry, revocation, and `clientAuth` EKU; the TLS handshake
itself is the proof of possession at login. A refresh on the held connection is an
application-level signed nonce, bound to the connection by its TLS exporter value (plan 7b),
since TLS 1.3 cannot re-authenticate a client (policy engine spec, §5.6). No secret crosses the
wire.

**OIDC** against the organization's existing identity provider. `port49 login` performs an
authorization-code flow; the broker validates the resulting token against the provider's
published JWKS. Requires no PKI, which removes an adoption barrier for organizations that
would otherwise have to stand a CA up first.

**Group membership is never taken from either credential.** It is resolved from the
directory at mint time (§10), so both paths converge on the same subjects, the same grants,
and the same policy. Where an OIDC provider is backed by the same directory, the two paths
are equivalent in everything but the proof of possession.

**The paths differ in what the agent holds for its session**, and it should not be glossed.

On the certificate path the agent's session **is a held mTLS connection** to the broker. The
hardware key is used once, at the handshake, and every mint for the rest of the day travels
over that connection — a 300-device Ansible run is one batch mint and no hardware interaction.
Nothing is written to disk. If the connection drops (sleep, agent restart), re-establishing it
is one more PIN or touch, and that is the fallback: a per-handshake challenge, never a
broker-issued session token, because such a token would be a bearer in a file and would erase
the property this path exists for. The PIV touch policy is the operator's choice; `cached` or
PIN-only is the sane default, since the key is exercised once per session rather than once
per device.

On the OIDC path the session is the identity provider's refresh token, held by the agent as a
public client with PKCE. It is a bearer on disk, usable by anyone who copies the file. The gap
is closable — after OIDC authentication the broker MAY issue a short-lived client certificate
whose key is generated locally in a TPM or OS keystore, giving hardware-backed session
protection without the organization running a CA. That is identified as the path for PKI-less
adoption and is **not required for v1**.

On both paths, extending a session at the ceiling requires a **fresh authentication event**
and takes `auth_time` from the new assertion (policy engine spec, §5.6).

**port49 is a relying party, not a certificate authority.** It validates certificates; it
does not issue, enroll, renew, or revoke them. Organizations using the certificate path
supply their own CA. The short-lived issuance described above would be the single, narrowly
scoped exception, and only for port49's own trust domain.

### Certificate-to-directory mapping

The principal extracted from a certificate must resolve to exactly one directory entry.
This mapping varies by PKI and MUST be configurable — SAN UPN, subject DN, SAN email, CN,
or an explicit attribute such as `altSecurityIdentities`.

Two requirements are security-relevant:

- **Ambiguity fails closed.** Zero matches denies; more than one match MUST deny loudly
  rather than selecting the first. Two users matching one certificate is an impersonation
  path.
- **Weak mappings MUST be issuer-pinned.** Matching on email or CN alone binds to a *name*
  rather than to a key, so a certificate from any other trusted CA bearing the same subject
  impersonates that user. Either use a strong mapping (issuer plus serial, or a SID
  extension), or verify the issuer alongside the searchable attribute. Weak mappings
  require explicit opt-in.

### Machine identity

Two supported mechanisms, in preference order:

1. **Kubernetes projected ServiceAccount token** (primary). The workload requests a token
   with an audience of `port49`; the kubelet writes and rotates it automatically. The
   broker validates it against the cluster's published JWKS and derives the identity
   `system:serviceaccount:<namespace>:<name>`. No CA, no certificate distribution, no
   rotation to implement, and no secret at rest.

2. **Issued workload certificate** (static hosts). Reuses the broker's existing
   certificate validation path with a separate trust anchor. The workload renews its own
   certificate ahead of expiry; only initial enrollment is manual.

SPIFFE/SPIRE is a viable third option for heterogeneous fleets but is **not** required and
is not a v1 dependency.

### Trust domain separation

Human and machine identities MUST be unforgeably distinct in the policy engine. A workload
identity MUST NOT be able to present as, or inherit the grants of, a human principal. This
is a small amount of code carrying a large share of the security value — so what it decides
on has to be stated.

**A principal's trust domain is whichever verifier validated its credential.** Configuration
declares the verifiers in two lists, and nothing else classifies:

```yaml
identity:
  humans:
    - {type: x509, trust_anchor: corp-users-ca}
    - {type: oidc, issuer: https://login.example.com/v2.0, client_id: port49-cli}
  machines:
    - {type: x509, trust_anchor: corp-workloads-ca}
    - {type: oidc, issuer: https://login.example.com/v2.0, audience: api://port49-svc}
    - {type: k8s,  jwks: https://kube.example.com/openid/v1/jwks}
```

The same issuer may appear in both lists with a different audience — an identity provider
that serves both people and application registrations issues both kinds of token from one
`iss`, and a claim in the token is not what tells them apart. Both keys are `aud` checks:
`client_id` names the public client whose ID token a human presents, `audience` names the
API identifier in the access token a service obtains through client credentials. A credential
accepted by no verifier is refused at mint. Policy identity strings carry the domain in their
form (policy engine spec, §2) so the same distinction is checkable in CI without a credential
in hand.

Service accounts therefore never authenticate with a directory password; port49 has no
password path at all. One authenticates as a workload certificate, a cluster token, or one
OIDC application per service, and may still map to its directory entry for group membership.

Groups are never taken from a credential, only from the directory. A deployment with an OIDC
provider and no directory — the PKI-less adoption path of §5 — therefore addresses humans
only through literal-identity subjects, which is workable for a small team and is the point
at which a directory earns its place.

## 8. Token model

### Two credentials, two lifetimes

| | Lifetime | Location | Operator cost |
|---|---|---|---|
| **Session** | 8–16h | agent: a held mTLS connection (certificate) or an IdP refresh token (OIDC); never on the wire | one authentication per day, plus one per reconnect |
| **Device token** | 30–900s; single-use, or reusable within the TTL for HTTP APIs | transient | none — minted automatically |

A single credential is not sufficient. One long-lived credential pasted into devices is a
password with an expiry date; one credential per authentication with no session forces a
certificate interaction per device.

### Token format: opaque handle

```
p49_7K2QF9XMRAVTC4EJHN6PBZ3D8W        (~30 characters)
```

The handle is a random secret, and all meaningful state lives in the store:

```
identity   principal derived from the certificate or workload token
groups     resolved from the directory at mint time
nas        the single device this token is valid for
```

**The store is keyed on `(nas, username)`, not on the handle value.** This is required for
CHAP. In a CHAP exchange the daemon never receives the token — it receives
`MD5(id ‖ secret ‖ challenge)` and must compute the same digest from the *plaintext* to
compare. A store keyed by handle value cannot be queried without the value, which would
make CHAP unimplementable while §14 requires it to be tested. Keying on `(nas, username)`
lets the daemon fetch the small candidate set for that user on that device and verify each.
Device binding becomes structural rather than a post-lookup comparison, and the handle
reverts to being purely a guessing-resistance secret.

A principal may hold several concurrent tokens for one device (see batch minting, §17), so
the store operation is **atomic match-and-delete within a keyed set**, not a plain
get-and-delete. §12's store interface reflects this.

The candidate set is bounded by construction rather than by filtering. Because expiry is
enforced by the store (below), an expired token is simply absent, and a redeemed one has been
removed — so the set contains only tokens minted for that username on that device within the
last `token_ttl` and not yet spent. In practice that is one, occasionally two or three. An
explicit cap (order of eight) is a backstop against a mint-loop defect, not the operative
bound — and it refuses the **mint**, with a typed error naming the count, never the
redemption, so a runaway client is told to stop while every token already issued stays
usable.

### Tokens and login context are encrypted at rest

CHAP requires the daemon to recover the token in the clear: the device sends
`MD5(ppp_id ‖ token ‖ challenge)`, and verifying it means performing the same computation.
The challenge is generated per attempt, so nothing can be precomputed at mint, and a stored
hash of the token is useless because the construction interleaves the challenge with the
token rather than digesting the token alone. Recoverable storage is therefore unavoidable for
any deployment using CHAP.

**Tokens are consequently encrypted at rest**, with the key held in the secret mount of both
components that touch them — the broker encrypts on write, the daemon decrypts on redemption
— which is the same place the RFC 8907 shared keys already live, so no new distribution
problem is introduced. The idempotency record (§17) holds a second copy of every token in a
mint response and is encrypted under the same key, expiring with the longest token it holds.

**Login context receives the same treatment**, for a different reason. It holds no credential,
but it holds identity — the principal, a certificate subject and serial, an OIDC `sub` — so
that revocation can reach a live device session (policy engine spec, §5.1.4). That is
PII-adjacent, and a store dump should not enumerate who was logged into which device.

This keeps the store from becoming a credential vault. A store compromise alone yields
nothing usable; an attacker needs the store *and* a daemon's or the broker's key. Because tokens live at most
`token_ttl`, key rotation is trivial — accept two keys for one TTL window, then retire the
older.

The residual is that a compromised daemon can decrypt. That is close to costless, since a
daemon with store access can already redeem any token it wishes.

Encrypting uniformly rather than only where CHAP is enabled is deliberate: one storage path,
no per-device conditional, and full RFC 8907 conformance without asking operators to give up
an authentication type the standard requires.

**`token_ttl` is therefore also the exposure window**, not only the replay window. A batch
mint of ten thousand tokens at `900s` keeps ten thousand recoverable secrets in the store for
up to fifteen minutes, including any the sweep never reaches. §17's batch minting SHOULD
therefore size the TTL to the sweep, or mint in waves, rather than treating a long TTL as
free. The concession §8 describes below is bounded for replay; it is linear for exposure.

**Rationale for an opaque handle over a self-describing signed token:**

- **Single-use enforcement is free.** A match-and-delete answers "has this been spent?"
  with the same operation that reads it — no separate replay-prevention store, no race
  between replicas. A signed token would require a nonce store to achieve the same
  property, making the "stateless" option strictly more complex.
- **Length.** TACACS+ field limits differ by authentication type, per RFC 8907 §4. In the
  authentication START packet every length field — `user_len`, `port_len`, `rem_addr_len`,
  `data_len` — is **one byte**, capping each at **255 bytes**. In CONTINUE and REPLY,
  `user_msg_len` and `data_len` are **two bytes**, allowing 65535.

  | Type | Password carried in | Ceiling |
  |---|---|---|
  | PAP | START `data` | **255 bytes** |
  | ASCII login | CONTINUE `user_msg` | 65535 bytes |
  | CHAP | START `data` = ppp_id (1) + challenge + response (16) | challenge ≤ 238 bytes |

  So **255 bytes is the binding protocol constraint**, set by PAP, and a ~30-character
  handle clears it by an order of magnitude. Devices impose their own, tighter input limits,
  which are what actually matter in practice. A signed payload carrying identity, groups,
  NAS, expiry, and a signature would not fit within safe bounds; 30 characters does.
- **Revocation is immediate.** Deleting the key ends it. A signed token is valid until
  expiry regardless of any action taken.

### Single-use means single-session, not single-packet

A strict delete-on-read design fails on the first retransmission. Devices retry: a TCP
reset between the daemon's read and its REPLY, a slow store crossing the device's timeout,
or the two independent server groups §13 *requires* all produce a second attempt with the
same token. Under delete-on-read that retry finds nothing, and the practical result is a
flaky login rather than a security property.

On redemption the daemon therefore replaces the token with a short-lived **receipt**
carrying the decision and the `ctx_id` it created, keyed
`(nas, username, credential_sha256)`. A retry within the receipt window (~30s) finds that
receipt only by presenting a credential that hashes to the same value, and then replays the
stored decision and reuses the recorded context rather than creating another. The replacement
is a single atomic store operation (§12).

**The credential hash is not optional, and it is in the key.** Without it the receipt would
authorize by `(nas, username)` alone, so for its lifetime anyone supplying that username with
*any* password would be admitted — the receipt would stand in for the very credential check it
was meant to survive. Putting the hash in the key rather than checking it after the lookup is
what makes "a genuine retransmission is the only thing that replays" structurally true: a
byte-identical retry finds its own receipt, and a genuinely new login by the same user finds
nothing and redeems normally. Checking the hash *after* a lookup that ignored it produced the
opposite — the user's second login within the window was answered FAIL `credential_mismatch`
with a failure-delay strike, leaving a fresh valid token unspent. That is why the key changed
on 2026-09-20 along with the context key (policy engine spec §13, decision 15).

**What the key no longer bounds is the line.** It used to be `(nas, port, user)`, so a replay
was confined to one line and, on platforms where `port` differs per transport, to one
transport. It is not any more: a spent token replays for `receipt_ttl` anywhere on that NAS,
over any transport — on vEOS an eAPI call (`port=command-api`) and an SSH login (`port=ssh`)
now share a receipt where they did not before, while on the N9Kv both were `0` and never
were separated. **`receipt_ttl` is now the only bound on a leaked spent token.** That is an
accepted cost, recorded in policy engine spec §13, decision 15.

The receipt is also what makes device-mismatch rejection the high-signal detection event
described below, rather than an event that also fires on ordinary packet loss.

**Presented credential** means what arrives in the packet, which is not always the token:
for PAP and ASCII it is the token itself, while for CHAP it is
`ppp_id ‖ challenge ‖ response`, which proves possession without carrying it. Hashing what
was presented rather than the token is what makes one rule work for all three.

One consequence for CHAP: a device that times out and *re-prompts* generates a fresh
challenge, so the new digest cannot match the receipt and the retry fails, requiring a fresh
mint. A byte-identical retransmission — the case that motivates the receipt — is unaffected.
This is accepted rather than solved, because the alternative is retaining the token itself in
the receipt.

### Expiry is enforced by the store

The broker writes with a **relative TTL**; the daemon performs an atomic match-and-delete.
Presence means valid; absence means expired or spent. Neither component writes or compares
a timestamp.

This removes clock synchronization as a *correctness* dependency — broker and daemon clocks
may disagree without producing an incorrect accept or reject. NTP remains necessary for
certificate validity checking and audit correlation, but is no longer a security
dependency of the token path. This is particularly important for multi-region deployments,
where components sit in different NTP domains.

### Device binding

Every token is scoped to exactly one device. Binding is structural: the store key is
`(nas, username)`, so a token presented from another device is simply absent there. Combined
with single-use and a short TTL, a captured token requires an attacker to replay it against
the specific device it was cut for, before legitimate use consumes it.

**The token carries a device tag so a wrong-device presentation is recognized, not merely
absent.** Absence alone cannot be told from an expired or mistyped token. The token is
therefore two parts:

```
token   = tag ‖ secret
tag     = base62(HMAC(k, device_id))[:6]       k: the key broker and daemons already share
secret  = 24 random base62 characters           ≈ 143 bits
```

A daemon computes its own tag once and compares it before any store access. A mismatch is
`device_mismatch`, certain and cheap, and it is the high-signal detection event — it does
not fire during normal operation. Because the tag is a keyed hash, a stolen token does not
reveal its target. Under CHAP the daemon never sees the token, so the tag is invisible and
the outcome is `token_not_found`; PAP, ASCII, and every HTTP-API transport get the
detection. The tag spends six of the thirty characters (L8).

### Username binding

The daemon MUST verify that the username presented at the device matches the one the token
was minted for. Without this the token is a bearer credential for whatever name the attacker
types, and accounting attributes the session to the wrong human.

The presented username is not the principal — `alice` rather than
`CN=alice,OU=netops,O=example`. The broker resolves the device-facing username at mint from
the same directory lookup that fetches groups, and machine identities declare theirs in
policy, since they have no directory entry. Usernames are unique across subjects, and
comparison is normalized for case and domain form. Specified in the policy engine spec, §2.

### Escalation credentials

`enable` is a separate authentication — usually on a new connection, with
`authen_service=ENABLE` and, on many platforms, a username of `$enab15$` rather than the
principal. No token exists for it, because the operator is already logged in and typing
interactively.

port49 therefore mints a **pair**: a login token and an enable token, both device-bound,
both single-use, sharing a TTL. Every relevant automation tool already has a second
credential field — `enable:` in Oxidized, `secret=` in Netmiko — so the pair drops into
existing configuration unchanged. Subjects that should not escalate are configured with no
enable mechanism and are refused.

On some platforms the enable exchange does not carry the principal's username, and login
context used to be keyed on `(nas, port)` for that reason alone. Measurement withdrew that
key on 2026-09-20: `port` is not the same value at authentication and at authorization on any
platform in the lab (policy engine spec §13, decision 15; §15, L1). **Login context is keyed
on `(nas, username)`**, and where the enable START carries `$enab{level}$` instead of the
principal it resolves through a `(nas, rem_addr)` secondary index, which refuses rather than
guesses when more than one context answers. That path is provisional on L3. Accounting
attributes the escalation to the real principal regardless of what the wire said. Mechanisms
and ceilings are specified in the policy engine spec, §7.

### Per-subject TTL

Token TTL is a **policy attribute of the subject**, not a global constant. An interactive
login needs ~60s, because mint and use are one SSH handshake apart. A batch job walking
thousands of devices needs a window matching the run.

Lengthening the TTL is a bounded concession: the token remains single-use and device-bound,
so a longer window widens replay opportunity on an *unspent* token only. Because it lives
in policy, the value is visible in review alongside the grants it accompanies.

## 9. Authorization model

> The engine is specified in full in
> [`2026-08-23-policy-engine-spec.md`](2026-08-23-policy-engine-spec.md). This section
> covers the shape and the reasoning; that document covers the grammar, evaluation order,
> schema, and platform behavior.

### Concepts

Templates do not compose, and they conflate *what* a principal may do with *where*. A
large fraction of apparently bespoke authorization profiles are in fact the same
permissions applied to a different device set. Separating the two collapses that
combinatorial growth.

The objects themselves — role, scope, subject, grant, privilege level, and the rest — are
defined in the taxonomy in §6. Three distinctions among them carry most of the weight:

**Device is a fact; Scope is a selector.** Inventory is imported and describes reality;
scopes are authored and describe intent. Without that split, `match: {site: us_west}` has
nothing behind it — TACACS+ gives the daemon a source address and nothing more, so device
attributes must come from an inventory (§10).

**Principal is runtime; Subject is policy.** A subject addresses a *set* of principals and
takes exactly two forms — an LDAP group, or a literal identity. One mechanism therefore
covers both directory-driven human access and hand-maintained service accounts, which are
otherwise two separate configuration systems.

**Privilege decides what the device will offer; the role decides what port49 will permit
within it.** These are not independent axes — the effective permission set is the
intersection, and the role is always a subset. A backup account needs `admin` privilege so
`show running-config` is *reachable*, while command rules confine it to `show`.

When port49 is unreachable, the device-local role the privilege level names is the policy
that remains. The role is what you get while port49 is watching; the privilege is what you
get when it is not. The device-local role must therefore be chosen as a sane approximation
of the port49 role, not as a formality.

```yaml
roles:
  - name: read_only
    privilege: readonly
    permit: [show **]

  - name: bgp_operator
    privilege: operator
    permit: [show bgp **, clear bgp /^[0-9]+$/ **]
    deny:   [clear bgp all]

scopes:
  - {name: us_west_edge, match: {site: us_west, role: edge}}
  - {name: all_devices,  match: {}}

subjects:
  - name: svc_bgp_automation
    identity: "system:serviceaccount:netops:bgp-automation"
    token_ttl: 120s
    enable: none

grants:
  - {subject: svc_bgp_automation, scope: all_devices,  roles: [read_only]}
  - {subject: svc_bgp_automation, scope: us_west_edge, roles: [bgp_operator],
     expires: 2026-12-01}
```

### Matching is structural, not textual

Rules match the **argument vector** the device actually sends — `cmd=show`,
`cmd-arg=bgp`, `cmd-arg=summary` — rather than a string reconstructed from it.
Reconstruction is lossy: the mandatory/optional flag is discarded, embedded whitespace
becomes indistinguishable from argument boundaries, and distinct requests collapse to the
same string. Rules match the full vector unless they end in `**`, so there is no
accidental substring match. Regex is available, confined to a single argument position.

This is not only a safety property. §9's own tooling requirement — that CI render *which
commands* a change adds or removes — is not computable over arbitrary regex. Choosing an
enumerable matching language is what makes the effective-permission diff real rather than
aspirational.

**Resolution is by specificity dominance**: a permit applies only when it is at least as
specific as every competing deny at *every* argument position, and strictly more specific
somewhere. Otherwise the deny stands.

There is exactly one deny mechanism. A global deny-wins rule is simpler to state but cannot
express an exception without negation, and RE2 has no lookahead — so a broad deny added under
pressure has no safe way to be narrowed. Dominance supplies exceptions in the grammar already
present, while keeping them honest: an exception must be at least as precise as the rule it
excepts, at every position that rule constrained. Naming a command does not buy back an
unrestricted argument.

The test is deliberately **one-sided** — a deny need not dominate anything, it wins by not
being beaten. So where a permit and a deny genuinely disagree about which argument matters,
no dominance exists and the safe answer follows automatically. Because specificity depends
only on the rule and the command, evaluation remains order-independent and the diff remains
exact. The guarantee that deny-overrides would have offered is replaced by visibility: CI
reports every shadowed deny and the permit that beats it.

**Entity names are classified, not canonicalized.** `deny: interface @management` means the
same thing on EOS, NX-OS, and Junos because each adapter declares which of *its* names belong
to the class. A rule referencing an undefined class fails at load, so the silent non-match —
a deny that quietly stops applying on the vendor nobody updated the regex for — cannot happen.

### Expiring grants

Grants MAY carry an `expires` date. Service accounts and temporary elevations otherwise
accumulate indefinitely. An expiry field with automated reminders makes temporary access
actually temporary and turns access review into a report rather than an investigation.

### Three evaluation points

| Point | Question | Data source |
|---|---|---|
| **Mint** (broker) | May this identity reach this device? | directory groups + scopes + inventory |
| **Session** (daemon) | What shell profile does this login get? | login context |
| **Per command** (daemon) | May this identity run this command here? | login context |

The middle point is the `service=shell` authorization with an empty `cmd`, which returns
`priv-lvl`, `shell:roles`, `local-user-name`, `idletime` and similar. It is where a large
share of deployed TACACS+ does *all* of its authorization — platforms such as Junos have no
meaningful per-command path — so it cannot be an afterthought. Vendor attributes are
rendered by the broker at mint from the device's platform into the blob, and the daemon
substitutes `{username}`, `{principal}`, and `{device}` from login context at each session
authorization (policy engine spec, §5.2), so it returns a precomputed list and never learns
what a platform is.

Evaluating device scope at mint time means an unauthorized target fails **before the
connection is opened**, rather than after login with a per-command denial.

### Login context

TACACS+ authorization requests carry a username but no token, and continue for the life of
a device login. The daemon therefore retains the resolved identity, the effective rule set,
and the rendered vendor attributes, keyed on **`(nas, username)`**.

The key deliberately excluded the username until 2026-09-20, because the `enable` exchange
arrives as a separate authentication whose username is on some platforms `$enab15$` rather
than the principal. The lab overturned that: `port`, the field the key used instead, is not
the same value at authentication and at authorization on any platform measured, so the key
could not find its own context — vEOS killed every session that got a vty, the N9Kv denied
every command. `port` and `rem_addr` are now recorded attributes of the context and are part
of no key. The `$enab{level}$` case, unmeasured on the only platform that has it, resolves
through a `(nas, rem_addr)` secondary index instead. Policy engine spec §13, decision 15
records the change and its cost: one user's concurrent sessions on one device share a
context.

**Login context MUST live in the shared store, not in process memory.** TACACS+ commonly
opens a new TCP connection per transaction, so authentication and subsequent authorization
requests may be served by different replicas.

**The broker cannot create login context.** The context key includes the device's tty or
vty string, which does not exist until the device opens the authentication exchange. The
broker instead writes its resolved result as an immutable, content-addressed policy blob
referenced by the token; the daemon creates context on redemption, holding the blob hash
rather than a copy. Because blobs are immutable, each replica caches them by hash with no
invalidation problem, and a batch mint across thousands of devices produces one blob per
platform rather than one per token. Specified in the policy engine spec, §5.1.1.

**Lifecycle.** Context is created only on successful token redemption. Teardown is ordered by
**authority**, not by reliability: port49's own redemption under the same `(nas, username)`,
revocation arriving from the identity layer, the local session ceiling, a username conflict on
a later exchange, and finally idle TTL. (A sixth trigger — an authentication attempt under a
different username, including one port49 rejects — was withdrawn with the re-key on
2026-09-20: a different username now addresses a different context.) Device accounting is
**advisory** — it annotates the context
and never deletes it, because a signal port49 did not generate and cannot verify must not be
able to discard state. `rem_addr` is recorded and compared on the enable exchange; the
username is the key. Because a stale context would otherwise be inheritable through
the `enable` exchange — which on many platforms carries `$enab15$` rather than a principal —
the automatic enable mechanism is available only where the platform sends a verifiable
username. Specified in the policy engine spec, §5.6.

**Reach.** Everything below acts at the next authorization request. On a platform that
authorizes only at login — Junos — and on any tier a device does not authorize, port49 can
neither warn nor revoke once the session is up; control there is bounded by the device's own
session, `explain` says so, and revocation records name the contexts they could not reach
(policy engine spec, §5.6).

**Session lifetime.** A credential's expiry bounds the *mint*, not the session. An OIDC
`exp` is commonly minutes, and a certificate's `notAfter` describes validity at
authentication; treating either as a session ceiling would end a router session every hour
for no security gain. The session clock is instead `auth_time + max_session_age`, set by
policy per role.

port49 can deny commands but has no way to close a session — there is no server-to-device
disconnect in TACACS+. Reaching the ceiling therefore never drops a connection, interrupts a
commit, or abandons a candidate configuration. The operator is warned in-session through
`server_msg` on the authorization reply, re-authenticates out of band while the session stays
open, and context survives a grace window so a late re-authentication resumes the session
rather than forcing a reconnect. This matters operationally: the failure mode of a session
limit must not be an engineer losing a half-applied change.

**Refresh policy.** Login context TTL SHOULD match the session lifetime and is refreshed by
the broker while the login remains active. Refresh MUST be
**refresh-ahead**: serve the cached value immediately and refresh in the background.
Synchronous refresh would place directory latency directly on the command path.

The cost is that a revoked principal may complete one additional command during the
refresh window — widening the revocation window by tens of milliseconds against a
five-minute refresh interval. The benefit is that per-command authorization is always a
single store lookup.

Effective revocation latency to a live session is therefore the sum of three windows: the
directory refresh interval, replication lag (§10), and the per-replica context cache TTL
(§12). The first two are minutes by nature; the third is a parameter port49 owns, and it is
kept to seconds so that it never dominates.

**Directory unavailable.** Serve stale context up to a hard staleness ceiling, alarming
throughout, then fail closed. The ceiling is a security parameter and MUST be explicit
configuration: `staleness_ceiling`, measured by the daemon against the context's
`refreshed_at`, denying `context_stale` with a `server_msg` once exceeded and resuming on the
next refresh (policy engine spec, §5.1.1, §5.6). Revocation does not function during the
grace window; this trade must be documented rather than left to operator judgment during an
incident.

### Tooling requirements

Policy is only reviewable if reviewers can see what changed in effect, not in text.

- **Effective-permission diff.** CI MUST render the effective change of a policy
  modification: which commands, on how many devices, added or removed. This requirement is
  what forces an enumerable matching language; it is not computable over arbitrary regex.
- **`port49 explain`.** Resolve a hypothetical decision and report the reason, including
  which role would grant a denied command. This is what allows requesters to self-serve
  rather than escalating. Where a control cannot be enforced on the target platform,
  `explain` MUST say so rather than reporting a decision the device will not honor.
- **Policy tests.** Assertions stored alongside policy and executed in CI against a
  file-backed inventory:

```yaml
tests:
  - {subject: svc_config_backup, device: dev-01, command: "show run",  expect: permit}
  - {subject: svc_config_backup, device: dev-01, command: "configure", expect: deny}
```

- **`port49 devices capabilities`.** Report, per device, what its platform is capable of
  authorizing against what it has been observed to authorize. A device with
  `aaa authorization config-commands` disabled looks entirely healthy while every
  configuration line goes unauthorized and unaccounted; this is the report that surfaces it.
  Operators MUST never be asked to assert device behavior the system can observe.

Policy tests are what make role refactoring safe, and are not achievable with rendered
templates.

### The decision log

A conventional TACACS+ deployment has one record of what happened: the accounting stream the
devices choose to send. It is incomplete by configuration — a device sending only privilege
15 commands reports nothing about the rest — it arrives after the fact, and it attributes
activity to whoever the shared password admitted.

port49 has a second and better record, because §7's identity model means it knows who the
person is and §9's evaluation means every decision passes through it. Every permit and every
deny is logged with the principal, the device, the command, the rule that decided it, and
the role that rule came from.

> **A decision must be reconstructible from its record alone.**

Records name the immutable, content-addressed blob they were decided against, so a decision
can be replayed and verified rather than believed — including against a later build, which
turns "did this release change anyone's access" into a diff. This is the compliance artifact,
and it is the one an existing TACACS+ server cannot produce at any level of effort, because
it never knew the person's name. Specified in the policy engine spec, §5.7.

**Two streams, one envelope.** Device accounting is still consumed and still emitted — it is
what identifies command tiers a device executes without authorizing anything — but it is
recorded as a *report*, sharing the decision log's envelope and sink while carrying weaker
guarantees. A single `ctx_id`, assigned when login context is created, joins both streams, so
one identifier reaches from an SSO login to a typed command. Accounting is never allowed to
enforce, and never allowed to discard state. Specified in the policy engine spec, §5.8.

## 10. External data sources

Two external systems feed the broker: the **directory**, which supplies group membership
for principals, and the **device inventory**, which supplies facts about devices. Neither
sits on the authentication hot path.

### Directory

The directory supplies **group membership only**. Entitlement semantics live in port49
policy under version control. This separation allows policy to be reviewed, tested, and
reverted without a directory change.

### Directory authentication

The broker binds as itself and queries the directory *about* a principal. It never binds as
the user — with certificate or OIDC authentication there is no user password to bind with,
and having the agent bind and report its own groups would be a self-asserted claim.

Three mechanisms, in preference order:

1. **SASL EXTERNAL over mTLS** (preferred). The broker authenticates with its own client
   certificate, which it renews itself. No password at rest and no rotation runbook. Active
   Directory advertises EXTERNAL and maps the certificate to an account, though the mapping
   must be configured deliberately — and the same strong-mapping requirement from §7 applies
   to the broker's own certificate.
2. **GSSAPI / Kerberos**. Native to AD and usually the easiest to get approved. The keytab is
   still a secret at rest, but it is rotatable and well understood operationally.
3. **Simple bind over LDAPS**. A bind DN and password. Most widely supported, weakest, and
   documented as such.

Whichever is used, the broker requires read access only.

**Nested groups MUST be handled explicitly.** `memberOf` is not transitive in Active
Directory, so a principal in a group that is itself a member of a granted group is invisible
to a naive read. AD requires `LDAP_MATCHING_RULE_IN_CHAIN` (`1.2.840.113556.1.4.1941`);
OpenLDAP requires a recursive search or a suitably configured `memberOf` overlay. This is the
most common cause of authorization that silently fails to apply, and it must be configuration
rather than an assumed default.

**Pre-warming requires a defined population** — a base DN and the set of watched groups —
otherwise there is nothing to enumerate ahead of an outage.

### Server pool

```yaml
directory:
  servers:
    - { uri: "ldaps://dc-01.corp.example.com", priority: 100, site: us-west }
    - { uri: "ldaps://dc-02.corp.example.com", priority:  90, site: us-west }
    - { uri: "ldaps://dc-03.corp.example.com", priority:  50, site: us-east }
  health_check:    { interval: 30s, timeout: 2s }
  circuit_breaker: { failure_threshold: 3, probe_interval: 60s }
  failback:        { stability_window: 5m }
```

- **Priority ordering** with failover to the next healthy server.
- **Health checking and circuit breaking**, so an unavailable server is skipped rather than
  retried on every request.
- **Sticky selection** — remain on the selected server rather than re-evaluating per query.
  Round-robin across replicas at different replication stages produces membership that
  appears to flap.
- **Failback hysteresis** — require sustained health before returning to a higher-priority
  server.
- **Site awareness.** All servers in the local site SHOULD be exhausted before crossing to
  another site. Inter-site directory replication may lag by many minutes, so failing to a
  remote site can move membership backward in time. Site crossings MUST be logged as
  consistency events.
- **Per-deployment locality.** The broker SHOULD derive its own site from the environment
  and sort `same-site-first, then priority`, so one configuration serves all regions
  without drift.

### Pre-warming

The broker SHOULD resolve group membership for the full operator population on a schedule
(hourly is sufficient), independent of activity.

Without pre-warming, the grace window protects only principals already active — a person
arriving during a directory outage has no cached membership and is denied. The dataset is
small (hundreds of principals), making this a cheap way to extend grace coverage to the
whole population.

### Replication lag

Effective revocation latency is `refresh interval + directory replication lag`. Quorum
across multiple servers is explicitly **rejected**: a majority vote on a partially
replicated removal reports the principal as still a member, making revocation slower, and
requiring agreement reduces availability relative to accepting any healthy server's answer.
Sticky selection with priority ordering provides a consistent view, which is the property
actually needed.

### Device inventory

TACACS+ carries no device identity — the daemon observes a source address and nothing else.
Every device attribute the design depends on (`site`, `role`, and critically `platform`)
therefore comes from an inventory, and the shared secret each NAS uses comes from the same
place. Inventory is specified in the policy engine spec, §10; three properties belong here
because they are architectural:

**Inventory is a snapshot, never a live query.** A separate component — the inventory
service (§6) — runs connectors against NetBox or Nautobot on a schedule and publishes a
versioned snapshot that the broker and daemon pull and cache. Querying a source of truth
synchronously at mint would put it on the authentication path, which is the same mistake §6
exists to prevent for the directory. Isolating the connectors in their own workload also
keeps source-of-truth credentials in one place and prevents a faulty third-party connector
from reaching the authentication path at all.

**Admission splits from inventory.** The address list is not the security boundary — the
shared key is, since a device connecting without the right key sends unreadable data.
Existence therefore comes from the source of truth, while *key assignment* stays in the
policy repository under review. The fleet is maintained once; the admission decision is still
a pull request.

**Change per sync is bounded.** A sync that would remove more than a configured share of
the fleet refuses, retains the last good snapshot, and alarms. A half-available SoT or a
mistyped filter would otherwise silently deauthorize the fleet. The service bounds each source
against what it gave last time, and each port49d bounds the document again, as it bounds its own
inventory file (policy engine spec §10, decision 28).

**Source-of-truth write access is privilege-granting.** If scopes match on synced
attributes, whoever can change a device's role in NetBox can move it into or out of a
scope, with no policy change and no diff. Scope-membership changes MUST therefore appear in
the sync diff, scopes MUST be able to pin device sets explicitly, and SoT write access MUST
be documented as privileged. The governing rule is that the source of truth supplies facts
about devices while the policy repository supplies intent — the moment an SoT tag can grant
a permission, authorization has left code review.

## 11. Protocol support

| RFC | Port | Status |
|---|---|---|
| **RFC 8907** — TACACS+ | 49 | Primary. The transport all deployed devices use. |
| **RFC 9887** — TACACS+ over TLS 1.3 | 300 | Implemented to spec, forward compatibility. |

Both listeners MUST be independently configurable and MUST be separable, per RFC 9887's
requirement that TLS and non-TLS services be distinct to prevent downgrade attacks.

RFC 9887 is implemented for standards correctness and future device support. **The product
does not depend on it**, because certificate identity is delivered through the RFC 8907
path.

### Listener limits

Port 49 is an unauthenticated TCP listener: anything that can route to it can open a
connection and send bytes. The governing rule is that **limits are per source before they are
global**, so one misbehaving or hostile device cannot deny service to the fleet. A global cap
reached first would turn a single flapping box into an outage.

- **Per-NAS concurrent connections** are capped. Devices commonly open a connection per
  transaction, so a flapping device or a broken retry loop otherwise consumes file
  descriptors without limit. Exceeding the cap refuses new connections from that source
  only; the device's own retry and server-group failover handle the rest.
- **Malformed input closes the connection**, counts against that source, and applies backoff: inside
  it, the source's new connections are refused at Accept with a reset, never held open (policy
  engine spec §10; §15 L28). A packet failing header validation (policy engine spec, §10) —
  including one with the unencrypted flag set — is never parsed further and its body is never
  logged.
- **A declined device is refused at Accept too.** A connection from a refused or quarantined device,
  or one a reload refused or removed, is recorded and reset at once. The source's next connections
  are refused at Accept with a reset for a short decline window, with no strike, and the window
  lapses when the device is admitted again or its quarantine ends (policy engine spec §10; §15
  L31).
- **Idle connections time out.** A connection that sends nothing holds a slot under the
  per-NAS cap; it is closed after a short, configurable idle period.
- **Repeated authentication failures from an admitted device** are counted per
  `(nas, username)`, answered with increasing delay, and alarmed. They **MUST NOT lock the
  account**: tokens are single-use and high-entropy, so this path protects resources and
  produces signal rather than defending a guessable credential — and locking out an operator
  mid-incident is a worse outcome than the attack it would prevent. **The delay's ceiling must
  stay under the shortest reply timeout of the devices it answers.** An operator who raises
  `limits.auth_failure_delay_max` above that timeout converts denials into fall-through: the
  device cannot tell a late FAIL from an unreachable server, so it takes the next method and
  accepts the local password. Measured timeouts are 3s to over 12s depending on the platform
  (policy engine spec §15, L13), which is why the default ceiling is 2s.
- **Accept-queue pressure sheds load rather than queueing it.** A request answered after the
  device has already given up is worse than a refused connection, because the device has by
  then failed over while the server still holds the work.

Every limit is configurable, and every limit has a metric and an alarm (§15) — a cap that
silently engages is indistinguishable from a bug.

## 12. Failure model

`✓` works · `⚠` degraded · `✗` fails

| Failure | New session | New device login | **Active login (commands)** | Batch run in progress |
|---|---|---|---|---|
| **Directory unavailable** | ✓ credential only | ⚠ ok within grace; else denied | ✓ stale context to ceiling | ⚠ as new login |

### Consequences

**Broker/daemon failure independence is a required property.** Broker unavailable means no
new access while everyone currently working continues. This is the correct degradation
shape for network AAA, and it holds only while the daemon never calls the broker
synchronously.

That property is **bounded by the staleness ceiling**, not unlimited. Login-context refresh
is the broker's job, so a broker outage lasting longer than the ceiling fails active logins
closed — deliberately, since serving indefinitely stale context would mean revocation never
takes effect. "Unaffected" therefore holds inside the grace window and not beyond it, and
the ceiling is the parameter that decides how long that is.

**The token store is the critical dependency.** It is the only failure that can break the
active-login column outright. Mitigations:

- **Hard timeouts** on all store operations, sized to the observed store round trip — a few
  multiples of it, ~50ms for a store in the same region, and necessarily above the
  cross-region RTT where the single global store of §13 is used, since every redemption is
  uncached by rule. A slow store must fail fast rather than hang; queued requests are worse
  than rejected ones. The value is deployment configuration, not a constant.
- **Circuit breaker** — after repeated timeouts, stop calling the store, serve from local
  cache, and probe periodically.
- **Per-replica read-through cache for login contexts**, with a TTL of **seconds, not
  minutes** — a context deleted by revocation on one replica stays valid on another until
  that replica's entry ages out, so the TTL is a term in revocation latency (§9) and MUST
  be explicit configuration. Under a store outage the circuit breaker serves the cache past
  its TTL, alarming, which is the store-side twin of the directory grace window: revocation
  does not function during it, and that is documented rather than discovered. Token
  redemption MUST NOT be cached — it is the single-use authority.
- **Connection pool separation** between token operations and login-context reads, so
  mint pressure cannot starve authorization.

This produces the correct degradation under a slow store: **new logins fail fast while active
logins continue** — but only on a replica that already holds that login's context and blob in
cache. A login whose commands land on a cold replica during a store outage is denied. Because
TACACS+ commonly opens a new connection per transaction, consecutive commands in one login
may reach different replicas, so the honest characterization is *degraded and uneven*, not
*unaffected*. Blobs help here: they are immutable and cached by hash, so the cache-miss window
is narrower than it would be for mutable state.

**Store health MUST NOT be wired into the readiness probe.** If all replicas become
unready simultaneously, the service loses all endpoints, devices declare the server dead,
and a degraded store becomes a total AAA outage. Serve from cache and alarm instead. This
holds for the Kubernetes readiness probe, which stays as written. For the TACACS+ listener
it is superseded by the owner's ruling of 2026-09-24: port49d closes its TACACS+ listener
while the store is unhealthy — after N consecutive failed checks, reopening after M passes —
so devices find the connection refused and fall to their local method. That outage is
deliberate: with the store down port49 can authorize nothing anyway (policy engine spec §5.7,
`store_unavailable`). It arrives with the remote store (plan 7).

The broker's own `/readyz` (plan 7c) follows the same rule: it answers whether the broker
is serving, and never the store, certificate status, or `broker.revocations_file`'s health,
which are alarms.

**Device-side AAA configuration is part of the failure model.** When TACACS+ servers are
declared dead, device behavior — retaining an existing shell profile while remote
authorization ceases — determines the outcome for logged-in operators. port49 MUST ship
tested reference AAA configuration per platform. That configuration is also what makes the
security argument in the policy engine spec's §5.6 true: it assumes a method list falls
through to local only when port49 is unreachable, never when port49 says no, and that is a
property of configuration rather than of the protocol — Junos with `password` listed in
`authentication-order` tries the local password on a reject (measured, lab register L4).
The reference configuration per platform is what disables fall-through on FAIL, and the lab
asserts it. The same
configuration decides what a **store outage** looks like, and there it cuts the other way:
measured 2026-09-24, with port49 up and its store failing, break-glass is refused outright on
IOS-XE and on Junos with `tacplus` alone, and on vEOS and the N9Kv it authenticates locally and is
then refused by the authorization port49 answers FAIL — thrown out at the exec authorization on
vEOS, every command refused on the N9Kv. Only an unreachable port49 lets break-glass work
everywhere (`tests/lab/results/L4-error-*.md`). The reference configuration has to be written
against that, not against "ERROR falls through".

**A key mismatch is indistinguishable from an outage, from the device's side.** A device
presenting a retired or wrong key gets no reply at all: port49d records its header, strikes
its source, and resets the connection at once, and refuses that source's next connections at
Accept with a reset for the strike's backoff (policy engine spec §10, "A key miss is closed at
once"). The device then falls to its local method as it does with port49d stopped: on vEOS, the
N9Kv, the C8000V and vJunos-router, break-glass logged in and ran its commands in the stopped
times, and every token login was refused (spec §15 L28; `tests/lab/results/L28-arista_eos.md`,
`L28-cisco_nxos.md`, `L28-cisco_iosxe.md`, `L28-juniper_vjunos-router.md`). This corrects what
this paragraph said before the lab: port49d first held the connection silent for the backoff,
which stalled a break-glass session's commands to 25–28 s on three of those images
(`L28-held-*.md`), and a FIN in place of the reset still cost the C8000V its own 5 s timeout
(`L28-fin-cisco_iosxe.md`). An open connection closed when its key version passes
`retire_after` gets the reset a reload's withdrawal sends, and on the same four images the
session survived it (spec §15 L29, `tests/lab/results/L29-reload-*.md`).
It is therefore the one row of this matrix that a
configuration change can cause, which is why key retirement is gated on the phase-out report
rather than on a calendar alone (policy engine spec, §10).

### Store interface

The store is accessed through a narrow interface, and the interface is the record set. Each
record names who writes it, who reads it, how it expires, and whether it is encrypted — this
table is the store plan:

| Record | Key | Writes | Reads | Expiry | Encrypted |
|---|---|---|---|---|---|
| token | `(nas, username)` → set | broker; broker deletes on revoke by principal, certificate, `sid`, or `(device, username)` | daemon: match-and-delete, or match-only for `reusable` | `token_ttl` | yes |
| receipt | `(nas, username, credential_sha256)` | daemon, atomically with the token removal | daemon | ~30s | yes — carries the decision and `ctx_id` |
| login context | `(nas, username)` | daemon creates; broker refreshes and revokes | daemon | idle TTL, extended by activity | yes |
| blob | `sha256` | broker | daemon, cached by hash | bumped to the longest referencing context; also emitted to the log | no — contains no identity |
| `contexts_by_principal` | principal → set of `(nas, username)` | daemon | broker | entries carry the context's TTL, or a sweep removes the dead | no |
| `contexts_by_sid`, `contexts_by_cert` | OIDC `sid`; `(issuer, serial)` | daemon; broker re-indexes `sid` on refresh | broker, on revocation | as above | no |
| `active_principals` | set of principal | daemon | broker, scheduled refresh | entries expire with the principal's last context | no |
| idempotency record | `(principal, Idempotency-Key)` + body hash | broker | broker | the longest `token_ttl` it holds | **yes — it contains the minted tokens** |
| idempotency reservation | the idempotency record, `pending`, with a random holder | broker, put-if-absent before the batch's first mint; completed or released by its holder alone | broker | 1 minute, or the completed record's | no — it holds no response |
| `tokens_by_principal`, `tokens_by_cert` | principal; `(issuer, serial)` → set of `(nas, username)` | broker, before each token | broker, on revocation | the token's TTL | no |
| revocation mark | `(principal, key)` or `(cert, (issuer, serial))` | broker, on `port49 revoke`; also kept in `broker.revocations_file` | broker, at every mint | none: until an operator lifts it | no — identity, no credential |
| failure counters | `(nas, username)`, source | daemon | daemon | short | no |

**Requirement:** the store MUST provide atomic match-and-delete with TTL, an atomic
remove-and-write for the token-to-receipt replacement (below), an atomic put-if-absent for
the idempotency reservation with a compare-and-set on its holder, and MUST be reachable from
every daemon a given device can reach. Topology is a deployment choice (§13). Because both
broker and daemon write login context, separation is by *operation* per identity, not by key
prefix.

Match-and-delete rather than get-and-delete because tokens are keyed on `(nas, username)`
to make CHAP implementable (§8), and one principal may hold several concurrent tokens for a
device.

**The match cannot be a single server-side primitive.** The store cannot compute
`MD5(ppp_id ‖ token ‖ challenge)`, nor decrypt. The operation is therefore two steps: the
daemon fetches the candidate set, decrypts and verifies locally, then performs an **atomic
remove-if-present** of the winning member — and the success or failure of that removal, not
the verification, is the single-use authority. An implementation that races two replicas
through this path MUST have exactly one of them observe a successful removal.

**The removal and the receipt write are one atomic operation** — a Lua script, a DynamoDB
transaction, a row lock — never two. Otherwise the replica that loses the race can read for a
receipt in the gap before the winner writes one, find nothing, and answer FAIL to a device that
is retrying precisely because the winner's reply was lost. The loser MUST read the receipt on
removal failure and, if it is absent, wait up to the store timeout before answering. The
receipt carries the winner's `ctx_id`, and a replay **adopts** that context rather than
creating a second one, so the correlation chain survives the retry it was built for.

A narrow interface makes the store pluggable (Redis, Valkey, DynamoDB, etcd, or an RDBMS)
rather than mandating one dependency, and permits an **in-memory implementation** so the
daemon can be integration-tested as a single binary with no external services.

## 13. Deployment requirements

Stated as requirements. Concrete topology is an operator concern and belongs in a
deployment guide.

**Source address visibility (critical).** TACACS+ carries no device identity in the
protocol; the server infers it from the TCP source address. Deployments **MUST NOT** apply
SNAT to device traffic, and the daemon **MUST** observe the true client source address.
A source-rewriting load balancer silently disables device binding — the check continues to
run but no longer means anything.

**Token store topology.** Because the mint follows the operator or workload while
redemption follows the device, the two may occur in different locations. Options:

| Topology | Trade |
|---|---|
| **Single global store** (recommended default) | Always correct. Cross-region latency on every cache miss, not only on redemption — see below; the store timeout of §12 must be set above that RTT or no remote region can redeem. |
| Regional stores + mint routed by target device region | Lowest latency. **Fails during regional failover**, when redundancy is most needed. |
| Regional stores with replication | Survives failover. Single-use enforced per-region, yielding a narrow replay window. |

**A global store does not confine cross-region latency to redemption.** Login contexts live
in the same store, so a per-command authorization that misses the local replica's cache
crosses regions too, as does every context refresh write. The p99 < 5ms target in §5 is
therefore conditional on **either a warm per-replica cache or a same-region store** — a
cross-region read alone can consume the entire budget.

Two things make the warm-cache case the common one rather than the hopeful one: blobs are
immutable and cached by hash, so they are fetched once per policy version per replica rather
than per login; and contexts are small, so caching them is cheap. But a cold replica taking
the first command of a login will see the round trip, and the target should be understood as
holding in steady state rather than at every instant.

**The policy file is a privilege.** `port49d` reloads `broker.policy_file` live, so whoever can
write it decides every operator's access within two `broker.policy_watch_interval`s (10s at the
default). The file and the directory holding it MUST be owned by `port49d`'s user or root and
writable by no one else; `port49d` refuses one that is not, at start and at every reload
(policy engine spec §5.1.3). That check reads owners and mode bits, so a POSIX ACL granting
write, or a writable directory further up the path, is the deployment's to keep closed. Write
the file atomically, by renaming a complete file over it.

**Independently upgradeable server groups.** Deployments SHOULD present two server groups
that are independently deployed and independently upgraded, with devices configured to use
both. Network-layer failover cannot detect a build that passes health checks but fails
authentication; only workload separation with staggered rollout protects against
correlated software failure. Two addresses in front of one workload provide no such
protection.

**Replica separation.** Pod anti-affinity and topology spread constraints are sufficient
for node and zone separation. Dedicated node pools are unnecessary absent a specific
hardware or compliance requirement.

**Connection handling.** Graceful termination with connection draining; a disruption budget
sufficient to preserve regional capacity during maintenance. Autoscaling SHOULD key on
connection count rather than CPU — the workload is I/O bound.

**Key rotation is scheduled work, not an incident response.** The RFC 8907 key lives in
device configuration, so no rotation is server-side only and every rotation is a fleet change.
port49 accepts every non-retired key version simultaneously, which removes the flag day: a
version is added, devices move at whatever pace the fleet allows, and the old version is
retired once nothing presents it. Deployments MUST therefore treat a rotation as a normal
change window with a device list, and MUST NOT plan one as a synchronized cutover. The
mechanism, the phase-out report, and enforced retirement are specified in the policy engine
spec, §10.

**A `lab:` block in `port49d.yaml` is never production** (owner's ruling 2026-09-24). It is the
lab's measurement instrument: seeded tokens minted at start and written to a file, a fault file
that makes the store fail on demand, and a fallback authorizer that answers seeded contexts
with the lab's fixed attributes and deny prefixes rather than a policy. port49d refuses none of
it, so it says so: with a `lab:` block present it prints one line to stderr at start naming
what the block enables and that it must never be in production. An operator who sees that
line in a production journal has a misdeployment, not a warning to tune out.

**Anycast note.** Anycast addressing gives automatic failover but interacts poorly with
long-lived TCP: a route change mid-connection lands packets on a server with no state for
that session. Deployments using anycast SHOULD prefer connection-per-transaction over
TACACS+ single-connection mode, trading cache locality for resilience to route changes.

## 14. Testing strategy

Integration testing uses **containerlab** with real network operating system images. The
single-dependency daemon design plus an in-memory store implementation makes these
topologies cheap to construct.

Required assertions:

- Full authentication flow against real devices, per platform and per authentication type
  (ASCII, PAP, CHAP).
- **Token minted for device A is rejected when presented from device B.** This passes
  trivially in a lab with direct connections and would regress the moment a source-
  rewriting proxy is introduced — it must be asserted explicitly.
- Single-use enforcement: a replayed token is rejected.
- **Retransmission is not a replay.** An identical retry within the receipt window succeeds;
  the same token from a different device, or under a different username, is rejected.
- Expiry: a token presented after its TTL is rejected.
- **Session authorization returns the correct vendor attributes per platform**, with
  mandatory versus optional flags honored. A mandatory attribute the platform cannot parse
  causes the device to reject the session outright, so this must be caught in the lab.
- **`enable` works** for all configured mechanisms, including the `$enab15$` username path
  resolving through the `(nas, rem_addr)` secondary index, and refusing when that index is
  ambiguous.
- Per-command authorization decisions match the policy test suite.
- **Config-command authorization is detected**: a device with `aaa authorization
  config-commands` disabled is identified and reported rather than appearing healthy.
- Every row of the failure matrix (§12): directory unavailable, store unavailable, store
  slow, broker unavailable, daemon unavailable, partition — including a device presenting a
  retired key, which from the device's side is indistinguishable from an outage.
- **Broker API** (§17): an interrupted batch mint retried with the same `Idempotency-Key`
  returns the original response and mints nothing further, including when the retry lands on
  a different replica; a batch spanning granted and ungranted devices returns per-item
  results rather than failing; a caller with no grant cannot distinguish an unknown device
  from an ungranted one; no endpoint returns a previously minted token; a request bearing
  neither a client certificate nor an OIDC assertion is refused; every mint produces a
  decision record naming the caller.
- Sustained load at the design target rate (§5).
- **Listener limits** (§11): a single source exceeding the per-NAS connection cap is refused
  while other devices continue unaffected; a malformed-packet flood does not degrade service
  to admitted devices; repeated authentication failures slow and alarm but never lock the
  account.
- **Observability** (§15): every MUST-alarm statement in both documents has a metric behind
  it, and no metric carries a device-identifying label.
- Device AAA fallback behavior per platform when servers are declared dead.

The policy engine spec, §14, lists the matcher-level assertions that do not require a
device image. Its §15 is the **lab register**: every claim about device behavior the design
rests on, with an ID, what depends on it, and whether it has been measured. The containerlab
step of the implementation plan is that table, and nothing about device behavior is asserted
elsewhere without citing an entry.

## 15. Observability

Three streams, with different shapes and different guarantees. Conflating them is the usual
mistake: the log answers *what happened to this person*, metrics answer *is the system
healthy*, traces answer *where did the time go*.

| Stream | Guarantee | Answers |
|---|---|---|
| Decision and accounting log (§9) | complete, never sampled | who did what, and why it was allowed |
| Metrics | aggregate, bounded cardinality | is the service healthy, is a rollout safe |
| Traces | sampled | which dependency consumed the latency budget |

### Every stated alarm needs a metric behind it

Both documents contain a substantial number of MUST-alarm statements — a snapshot growing
stale, a `rem_addr` mismatch on enable, a rotation approaching its retirement date with
devices still on the old key, an accounting spool dropping records, a local fallback
succeeding for a name port49 knows. **The metrics set is derived from those statements rather
than invented separately**, and an alarm with no metric is an unimplemented requirement.

The daemon exports, at minimum: request counts and latency histograms per exchange type;
decisions by event, verdict, and reason, using the same closed vocabulary as the log; login
context operations by trigger; store operations by outcome, plus circuit-breaker state; blob
cache hit rate; key validations by `key_ref`, version, and outcome; unvalidated packets by
diagnosis; accounting spool depth and drops; snapshot age and bundle version; and connection
counts against the per-source limits of §11.

The broker exports: mints by status and reason; mint latency; directory query latency and
errors; idempotency replays; and outstanding unspent tokens, which is the exposure window of
§8 expressed as a gauge.

### Cardinality is a design constraint, not a tuning exercise

**Device identity does not belong in metric labels.** Ten thousand devices multiplied across
several metrics produces a series count that will either bankrupt or destabilize the metrics
backend, and it is the single most common way an observability design fails in this shape of
system.

Labels are bounded: platform, `key_ref`, reason code, outcome, exchange type. Per-device
questions — *which* devices are still on the old key, *which* device is failing
authorization — are answered from the log stream, which already carries device identity on
every record and is built to be queried that way. This is why the reports in the policy
engine spec are CLI commands over the log rather than dashboards over metrics.

### Tracing

OpenTelemetry, with a span per protocol exchange and per store operation.

TACACS+ carries no trace context, so a trace cannot be propagated from the device — it begins
at the daemon. The mint is a separate trace on the broker, and the two are joined after the
fact by `ctx_id` and `token_sha256` carried as span attributes — never the token — rather than by attempting
propagation through a protocol that has nowhere to put it.

**Traces may be sampled; the decision log never is.** They answer different questions, and a
sampled audit trail is not an audit trail.

## 16. Language: Go

**Decision: Go.**

- **Performance requirements are modest.** The design target is dominated by store and
  directory round-trips, not computation. Go has substantial headroom; the argument for a
  systems language would apply to a line-rate packet processor, which this is not.
- **Ecosystem fit.** Mature, well-maintained libraries for Kubernetes, LDAP, Redis, and
  TLS. The alternatives' equivalents are less developed for exactly these dependencies.
- **Contributors.** This project's viability depends on adoption by network engineers,
  for whom Go is the lingua franca of the surrounding ecosystem (Kubernetes, Prometheus
  exporters, containerlab). A less accessible language would materially shrink the
  contributor pool.
- **Concurrency model** fits connection-per-transaction TCP with many short-lived handlers.
- **Single static binary** with straightforward cross-compilation, which matters for the
  CLI distributed to operator workstations.

**Argument against:** the TACACS+ parser consumes untrusted binary input, where stronger
memory-safety guarantees have real value. Go is memory-safe; the realistic residual risk is
logic error in the parser, addressed by fuzzing in either language. Not sufficient to
outweigh the ecosystem and contributor considerations.

## 17. Broker API and client libraries

The **HTTP API is the product; libraries are conveniences.** Every language binding is a
permanent maintenance obligation, so the API has to be callable in a few lines from anything
that speaks HTTP, and the ecosystem supplies the rest.

### Surface

```
GET   /v1/config          unauthenticated — issuer, client_id, scopes: how to authenticate
POST  /v1/tokens          mint, one device or many
POST  /v1/tokens/revoke   mine; by principal or (device, username); OIDC sid with plan 7h; a token is never sent back
POST  /v1/refresh         re-authenticate; extends live login contexts
POST  /v1/refresh/challenge  certificate path: a single-use nonce the agent signs for /v1/refresh
GET   /v1/identity        what port49 resolves the caller to — principal, groups, grants
POST  /v1/explain         a hypothetical decision, without minting
POST  /v1/logout          OIDC back-channel logout — IdP-initiated, carries a logout_token
GET   /healthz  /readyz   unauthenticated; readiness is serving or not, never store health (§12)
```

**Errors.** These are the API's own codes, not reason codes: each request's decision record keeps
its policy engine spec §5.7 reason.

```
409  idempotency_in_progress          a duplicate of a request still minting under the same Idempotency-Key (plan 7a)
400  bad_request                      among others, a device named twice in one request (plan 7a)
403  api_right_missing                the call names another principal, or a (device, username) whoever holds it, and the caller's subject declares no api: right that unlocks it (plan 7c)
503  revocation_busy                  another revocation or lift held the revocation slot for 10 s, or the caller's own self or key revocation is still running (answered at once); nothing was revoked; no record; Retry-After (plan 7c)
500  broker_error                     /v1/explain: the broker could not work out the answer, a fault a mint reports as the item error broker_error; the explain record carries explain.mint_error and no verdict (plan 7c)
401  refresh_challenge_missing        /v1/refresh with no outstanding challenge on this connection, or a stale one
429  refresh_too_soon                 a refresh on this connection less than 10s after the last; Retry-After
503  certificate_status_unavailable   the certificate's status could not be established (on_unavailable: refuse); Retry-After: 60
```

`/v1/config` is unauthenticated by necessity: a caller that does not yet know how to
authenticate needs somewhere to ask. It returns discovery data only — never fleet
information.

### Minting

Targets are named, not addressed: a device name or a `scope`, resolved through inventory.
A raw address that inventory does not know is refused, because inventory membership is the
admission boundary (§10). The response carries the address back, since the caller usually
needs it to connect.

**The address is a fact from the source of truth, and the client MUST NOT trust it further
than it trusts an SSH host key.** Whoever can add an address to `core-sw01`'s record can list
a host they control; `port49 ssh core-sw01` would connect to it, its SSH server would prompt,
the agent would supply the token, and the attacker would replay it against the real device
within the TTL from the real device's address — device binding and single-use both hold,
because the legitimate login never happened. The agent and every shipped client therefore
verify host keys and never accept a first-seen key silently for a device inventory already
knows. Inventory MAY carry a host-key fingerprint per device; where it does not, the first
verified connection pins one through an explicit `port49 devices trust` step. An address
added to an existing device is a security event in the sync diff (policy engine spec, §10).

`ttl_seconds` is a request, not an instruction — the broker clamps it to the policy maximum
for that subject and reports what was actually granted. `enable: true` requests the minted
escalation pair (§8).

On a batch, the TTL is also the exposure window: every unspent token sits recoverable in the
store for its whole life (§8). A sweep SHOULD therefore size the TTL to the sweep or mint in
waves, and the API SHOULD make the granted expiry visible per item so a client can tell it
asked for more than it will use.

### Requirements

**Every call is authorized as a principal, and by default a principal acts only on itself.**
Mint, revoke, explain, and identity apply to the caller's own tokens and contexts unless the
caller's subject declares an `api:` right — `revoke_others`, `explain_others`, `sync`,
`keys_show`, `replay` — in the policy repository (policy engine spec, §2). Without this,
any principal who can complete an SSO login could revoke another operator's live router
sessions mid-change. `/v1/logout` is the exception: it authenticates by the identity
provider's signature on the logout token, not by a caller. Every subject carrying `api:` is
in the CI report.

As built (plan 7c; policy engine spec §13 decision 34): a principal ending its own sessions
leaves no standing mark; revoking another principal is the admin socket's standing mark, its
origin the caller; `sync`, `keys_show` and `replay` are reserved until an endpoint they guard
exists; and every authenticated call is recorded (policy engine spec §5.7).

**Idempotency is mandatory, not a convenience.** Tokens are single-use, so a batch mint that
times out mid-flight leaves the caller unable to retry safely: it cannot know whether it
burned four thousand tokens. The broker MUST key the response on
`(principal, Idempotency-Key)` for a window exceeding any plausible client retry and replay
it verbatim. A retry that reaches a different broker replica MUST behave identically, so the
record lives in the store rather than in process memory. The record also holds a hash of the
request body: the same key with a different body is refused as a conflict, never replayed,
since a client that reuses a key for a new request would otherwise silently receive tokens
for the wrong devices. Two requests under one key must not both mint: the broker reserves
the key for every device of a batch, put-if-absent, before it mints the first, so a concurrent
duplicate is answered `409 idempotency_in_progress` and a different body `409
idempotency_conflict`, and the reservation is completed with the response, or released when its
device is refused, by the request that holds it and no other (plan 7a).

**Partial failure is reported per item, never at the top level.** Any sweep over a scope
includes devices the caller holds no grant on. Failing the whole call would make batch
minting unusable, and callers would work around it by minting one device at a time — which is
the overhead batch minting exists to remove. `status` and `reason` MUST use the same closed
vocabulary as the decision log (policy engine spec, §5.7), so the API response and the audit
record agree.

**No API keys, ever.** Callers authenticate with mutual TLS or an OIDC assertion, resolving
to a principal by the same identity model as an interactive login (§7). A minting API key
would be a long-lived shared secret guarding the service whose purpose is removing long-lived
shared secrets — and a worse one than the device key it replaced, since a single key would
mint for the entire fleet.

**Write-once.** Tokens appear in the mint response and nowhere else; there is no endpoint
that reads a token back. A compromised session can mint — which is logged, attributable, and
revocable — but cannot enumerate what other principals hold.

**Batch is capped and the caller pages.** A ten-thousand-device sweep chunks client-side.
Server cost stays low because a batch collapses to one blob per platform (policy engine spec,
§5.1.1), but an unbounded request is a memory and tail-latency hazard.

**The broker's listener is limited per source and per principal, before globally** (§11's rule).
The broker completes each TLS handshake itself, within 10 s, and counts every failure by reason.
One source address holds a bounded number of connections not yet bound to a principal, and the
next is reset at accept; one principal holds a bounded number of held connections, and a new one
closes the oldest of its own certificate, else the principal's oldest, so an operator whose laptop
slept is never locked out by their own dead connections, and one certificate cannot hold every
slot for `max_session_age` (plan 7a). A revoked certificate's connection is answered
`credential_revoked` and closed as it binds, so its agent ends the session (spec §5.1.4).

**A revocation reaches the held connection.** A revoked principal's or certificate's held
connections are closed, and every mint it would make is refused, before and after the mint's token
writes, until an operator lifts the revocation: otherwise a token minted after the revocation
would lift it at the next login (policy engine spec §5.6, §13 decision 15; plan 7a).

**Every call is a decision record.** A mint emits the `mint` event (policy engine spec, §5.7)
naming the caller's credential hash, the grants that matched, and the resulting blobs. An API
that mints authority without an audit trail would defeat the point of the product.

**Errors are typed, and never leak fleet data.** A caller with no grant on a device MUST NOT
be able to distinguish "this device does not exist" from "you have no grant on it" — otherwise
the mint API becomes a fleet enumeration oracle for any authenticated principal.

### Internal interfaces

The same rule applies inward: **every internal call authenticates as a workload identity, and
no interface accepts a shared bearer token.** A compromised pod network must not be able to
trigger a sync or read the fleet list simply by being on the network.

| Caller → callee | Identity | Permitted |
|---|---|---|
| daemon → inventory service | workload certificate, listed in `readers` | read a snapshot |
| daemon, broker → token store | store-native auth over TLS | the operations §12's record table assigns to it |
| broker → directory | §10's directory authentication | read group membership |
| operator or CI → `POST /v1/sync` | operator or CI certificate, listed in `syncers` | trigger a sync |
| connector → NetBox / Nautobot | source-of-truth credential | read devices, with a read-only token: the service never writes |
| NetBox / Nautobot → inventory service webhook | HMAC-SHA512 of the body under the source's webhook secret, over TLS on `webhook_listen` | trigger a sync of that source; nothing in the delivery reaches the bundle |

Three consequences worth stating:

**Reading a snapshot is not the same right as triggering a sync.** The daemon holds only the
first. A sync reaches an external system and can change what the fleet looks like, so it is an
operator action even though it is exposed as an API.

**A webhook is the one inbound call without a workload identity, and its secret is not a bearer
token.** No source of truth can present a client certificate (policy engine spec §10), so a
delivery is authenticated by HMAC-SHA512 of its body. The secret is never sent with a delivery,
and the service checks the signature in constant time. A host on the network without the secret
can trigger nothing. A holder of the secret, which includes anyone the product lets read its
webhooks, can make the service sync one source, which is bounded and reads only that source, and
nothing else.

**Key material never enters the snapshot, and neither does key assignment.** A snapshot carries
a device's facts; port49d resolves each device's `key_ref` from its own policy's key groups and
the key from the secret manager. Someone who obtains a snapshot learns the fleet, which is worth
protecting, but not a single key or which key a device speaks (policy engine spec §13,
decision 30).

The token store is the one place where a password may still exist, since store-native
authentication is whatever the chosen store offers. It is scoped per component and rotated
like any other credential (policy engine spec, §10).

### Client libraries

The **CLI is the universal client** — anything able to execute a subprocess is integrated.

| Artifact | Scope | Priority |
|---|---|---|
| `port49` CLI | login, token, explain, test, SSH integration, agent | v1 — primary effort |
| Python library | read identity, mint, batch, retry (~300 lines) | v1 |
| Ansible lookup plugin | thin wrapper over the Python library | v1 |
| Go library | falls out of the daemon implementation | opportunistic |

Machine workloads require no agent: identity is a file and minting is a single request.
Only interactive human use requires session management and SSH integration.

A library's job is the ergonomics the raw API deliberately leaves out: chunking a large
sweep, generating an `Idempotency-Key`, retrying on it, and turning per-item `denied` results
into something the caller can act on.

## 18. Open questions

1. **License — decided: Apache-2.0.** Chosen for the explicit patent grant and because it
   is the least friction for corporate adoption of an infrastructure component. To be
   applied before the repository is made public.
2. **Token store topology.** Global versus regional (§13) — a deployment decision, but the
   recommended default should be validated under load.
3. **Single-connection mode versus anycast.** Cache locality against resilience to route
   changes (§13). Requires measurement.
4. **Device-side credential input limits** per platform. The protocol ceiling is settled
   (§8: 255 bytes, set by PAP), so what remains is what each network OS will actually accept
   at a password prompt. Measured in the containerlab matrix, not from documentation.
5. **Unattended automation — resolved for sequencing.** Configuration backup runs as
   unattended cron on static hosts, making the workload-certificate path a day-one
   requirement rather than a later addition; §19 reflects this. The Kubernetes
   ServiceAccount path remains the preferred mechanism where it is available and follows.
   Multi-identity subjects (policy engine spec, §2) make the eventual migration a policy
   no-op.
6. **Login context refresh cost** at the design target: active session count times
   refresh frequency against directory capacity.
7. **Engine decisions — closed.** All questions raised against the policy engine are
   resolved, with reasoning recorded in the policy engine spec, §13. Two items are
   deferred there with stated triggers rather than left open: inventory-sourced entity
   classes, and per-platform projection equivalence (a containerlab work item, not a
   design question).

## 19. Sequencing

The order is chosen so that the product's core claim — a real identity reaching a real
device with no shared password — is demonstrated **before** the policy engine and inventory
service are built out, because that path holds the unknowns the lab register (policy engine
spec, §15) exists for: the 255-byte input limit, `server_msg` display, `port` contents, and
whether API transports authenticate per request. An engine built ahead of that evidence is
built against a guess.

1. TACACS+ protocol implementation (RFC 8907) with an in-memory store; containerlab
   harness against real device images; header validation and listener limits; accounting
   record parsing. Lab register entries L1, L2, L5, L6, L8, L10 close here.
2. Token model: mint, redeem, device tag and binding, single-use with receipts, TTL,
   encryption at rest, the store record set, and a store reachable by two processes (the
   in-memory store of step 1 is in-process) — **the last not built**: plan 2 shipped the sealing
   layer over the in-process store, so step 3's broker runs inside `port49d`, and a store two
   processes can reach is owed before the broker becomes a process of its own (step 7).
   Reusable tokens are built here but stay provisional until L7 closes.
3. **Vertical slice.** A minimal broker — certificate validation against one trust anchor,
   literal-identity subjects, a file-backed policy with roles and grants but no scopes beyond
   `all_devices` — and the agent's `login` and `token` commands over a held mTLS connection.
   First real login to a real device. The slice borrows ahead: a hand-written admission
   snapshot and key group (step 6), a single blob written and read (step 4), and one
   platform's session attributes (step 5), each in its simplest form. Step 3 measures L7's
   eAPI `/login` clause; L7 stayed open on NX-API's `nxapi_auth` cookie until that was measured
   by hand on 2026-09-24 and the row closed (`tests/lab/results/L7-nxapi-cookie-cisco_nxos.md`). L3 closed in the lab work before it. L4, measured
   over SSH on all five images including IOS-XE, stays open on `deadtime`, the transports it
   has not measured, and authorization fall-through (policy engine spec, §15).
4. Policy engine in full: normalization, matcher, scopes, `explain`, policy tests, the
   decision log and replay. It borrows ahead from step 5 in the simplest form: a built-in
   table of each shipped platform's dialect — pipe token, entity classes, level rendering —
   with every value either measured and cited or chosen in the direction that fails closed.
5. Platform adapters: built-in definitions, entity classes, user overrides, pinned platform
   set, projection for session-only platforms. L9, L11, and L12 govern this step; the
   projection generator is not final until L12 closes (spec §13, decision 22).
6. Inventory service: file inventory, bundle API, daemon pull-and-cache, NetBox and
   Nautobot connectors, bounded-change safety, quarantine, capability inference.
7. Broker in full: OIDC, certificate-to-directory mapping, directory integration, pre-warm,
   grace, context refresh, revocation, the API authorization model.
8. Machine identity, workload certificate path: enrollment, self-renewal, multi-identity
   subjects. Unattended automation — configuration backup on cron — is a day-one consumer,
   and it runs on static hosts where the Kubernetes path does not apply.
9. Agent in full: SSH integration with host-key verification, the OIDC public client.
10. Machine identity, Kubernetes path: projected ServiceAccount token validation.
11. RFC 9887 TLS 1.3 listener.
12. Deployment artifacts, reference device AAA configuration, load validation.
