# port49 — Design

**Status:** Draft
**Date:** 2026-08-21
**Language:** Go

---

## 1. Summary

port49 is a TACACS+ server that delivers **certificate-based user identity** to network
devices that will never support certificates themselves.

An engineer authenticates once per day — with a hardware-held certificate (PIV, YubiKey, or
equivalent) or against the organization's existing OIDC provider.
For each device login, a local agent transparently mints a **short-lived, single-use,
device-bound token** and supplies it where the device expects a password. The device
performs an ordinary RFC 8907 TACACS+ exchange and requires no configuration change
beyond pointing at port49.

The user's credential never crosses the device's wire. Only a token derived from it does,
and that token is worthless the instant it is spent.

---

## 2. Problem

TACACS+ remains the standard for network device AAA, and its per-command authorization
and accounting have no real substitute. But the deployed protocol has three problems:

**The transport is weak.** RFC 8907 obfuscation is MD5-based and not a security boundary.
RFC 9887 (2025) replaces it with TLS 1.3 and mutual certificate authentication — but no
mainstream network OS ships a TLS-capable TACACS+ *client*. Server-side support exists;
there is nothing to talk to. Any design that depends on RFC 9887 for identity has its
ship date set by hardware vendors.

**Authentication is still a password.** Even inside a TLS tunnel, RFC 9887 authenticates
the *device* to the server. The human at the CLI still proves identity with a password
carried in an ASCII, PAP, or CHAP exchange. Certificate identity for the *user* is
unsolved.

**Operations do not scale.** Existing implementations are mature and correct but assume a
different era: single-process daemons with local configuration files, bespoke config
languages, and shared secrets that in practice are never rotated. Authorization is
commonly maintained as rendered templates, which do not compose — each new account or
variant requires forking a template, making the platform owner a permanent bottleneck in
a ticket queue.

---

## 3. Goals

- **Strong user identity on unmodified network devices** — hardware-held certificates or
  the organization's existing OIDC provider, neither of which the device ever sees.
- **Standards compliance.** Strict RFC 8907, with RFC 9887 (TLS 1.3) implemented to spec
  for forward compatibility.
- **Declarative, reviewable authorization policy** — composable roles and scopes under
  version control, replacing hand-maintained templates.
- **Machine identity for automation** with no long-lived secret at rest.
- **Horizontal, container-native scaling** with no local state on any replica.
- **Predictable, documented degradation** when dependencies fail.

## 4. Non-goals (v1)

- **SSH certificate authority / device-native SSH cert auth.** A viable complementary
  approach, deliberately deferred. The shared policy core does not preclude it later.
- **RADIUS / RadSec.** Out of scope.
- **Replacing device-local break-glass accounts.** These remain the recovery path of last
  resort and must not depend on port49.
- **General-purpose policy engine.** Policy is scoped to network device AAA.

---

## 5. Design targets

Stated as requirements, not as observations of any particular environment.

| Target | Value |
|---|---|
| Network devices | 10,000 |
| Sustained authentication rate | ~170/sec (10k devices on a 60s poll interval) |
| Per-command authorization latency | p99 < 5ms |
| Scaling model | stateless horizontal replicas |
| Directory dependency | must not sit on the authentication hot path |

The sustained rate is driven by high-frequency pollers (metrics collection scripts),
which are the heaviest consumers — far exceeding interactive human logins.

## 6. Architecture

```
  Engineer laptop                                Network device
  ┌────────────────┐                             ┌──────────────────┐
  │  port49 agent  │                             │  TACACS+ client  │
  │  + credential  │                             │  (unmodified)    │
  └───────┬────────┘                             └────────┬─────────┘
          │ ① authenticate (cert or OIDC), hold session   │ ③ TCP/49 (RFC 8907)
          │ ② mint device-bound token                     │    TCP/300 (RFC 9887)
          ▼                                               ▼
  ┌────────────────────┐   token handle          ┌──────────────────┐
  │      Broker        │ ─────────────────────▶  │      Daemon      │
  │  · validates ident │   (via the operator     │  · TACACS+ proto │
  │  · resolves groups │    or the agent)        │  · redeems token │
  │  · evaluates scope │                         │  · per-cmd policy│
  │  · mints tokens    │                         │                  │
  └─────────┬──────────┘                         └────────┬─────────┘
            │                                             │
            ├──────────────▶ Directory (LDAP/AD)          │
            │                (groups only, cold path)     │
            │                                             │
            ├──────────────▶ Inventory service ◀──────────┤
            │                (snapshot pull, cold path)   │
            ▼                                             ▼
       ┌──────────────────────────────────────────────────────┐
       │                    Token store                        │
       │  · token handles (strong consistency, single-use)     │
       │  · session contexts (eventual, cached at each daemon) │
       └──────────────────────────────────────────────────────┘
```

### Components

**Agent / CLI (`port49`).** Holds the operator's session, mints tokens on demand, and
integrates at the SSH layer so existing workflows are unchanged. Also provides
`login`, `token`, `explain`, and `test` subcommands. Machine workloads do **not** require
the agent — identity is a file and minting is a single HTTP call.

**Broker.** The only component that talks to the directory. Validates client identity
(certificate, OIDC token, or workload token), resolves group membership, evaluates device scope, and
mints token handles. Fails independently of the daemon.

**Daemon.** Speaks TACACS+. Redeems token handles, evaluates per-command authorization
against session context, and emits accounting. **Never contacts the directory.**

**Inventory service.** The only component that talks to a source of truth. Runs connectors
(NetBox, Nautobot, and others), applies bounded-change safety, and publishes a versioned
device snapshot over a small read-only API. Broker and daemon *pull and cache* that snapshot;
neither ever queries it per request. It is the one component permitted to be a singleton,
because nothing depends on it being up.

**Token store.** Holds token handles and session contexts. Accessed via a narrow
interface (see §12).

### Key architectural rule

> **The daemon's only hot-path dependency is the token store.**

The broker owns every directory interaction, including background refresh of live session
contexts. The inventory service owns every source-of-truth interaction. This keeps an
unreliable or slow directory entirely off the authentication and authorization hot paths, and
makes the daemon trivially testable with neither a directory nor an inventory present.

The daemon does hold one **cold** dependency: the device admission snapshot, which it needs
to accept a connection at all. That snapshot is pulled at startup, refreshed in the
background, persisted locally, and **never expires** — a stale device list is a far smaller
problem than no device list, and an admission table with a TTL would let a prolonged sync
outage halt authentication fleet-wide. Stating this explicitly is better than quietly bending
the rule.

## 7. Identity model

### Human identity

Two supported paths, both first class. They differ only in how a human proves identity;
everything downstream is identical.

**X.509 client certificate** presented over mutual TLS to the broker. The private key is
generated on a hardware token — PIV, YubiKey, or equivalent — and never leaves it. The
broker validates the chain, expiry, revocation, and `clientAuth` EKU, then challenges the
agent to prove possession of the key. No secret crosses the wire.

**OIDC** against the organization's existing identity provider. `port49 login` performs an
authorization-code flow; the broker validates the resulting token against the provider's
published JWKS. Requires no PKI, which removes an adoption barrier for organizations that
would otherwise have to stand a CA up first.

**Group membership is never taken from either credential.** It is resolved from the
directory at mint time (§10), so both paths converge on the same subjects, the same grants,
and the same policy. Where an OIDC provider is backed by the same directory, the two paths
are equivalent in everything but the proof of possession.

**The paths differ in one security property**, and it should not be glossed. The 8–16 hour
session credential is a hardware-held key in the certificate case and a bearer token on
disk in the OIDC case; the latter is usable by anyone who copies the file. The gap is
closable — after OIDC authentication the broker MAY issue a short-lived client certificate
whose key is generated locally in a TPM or OS keystore, giving hardware-backed session
protection without the organization running a CA. That is identified as the path for
PKI-less adoption and is **not required for v1**.

**port49 is a relying party, not a certificate authority.** It validates certificates; it
does not issue, enroll, renew, or revoke them. Organizations using the certificate path
supply their own CA. The short-lived issuance described above would be the single, narrowly
scoped exception, and only for port49's own trust domain.

### Certificate-to-directory mapping

The principal extracted from a certificate must resolve to exactly one directory entry.
This mapping varies by PKI and MUST be configurable — SAN UPN, subject DN, SAN email, CN,
or an explicit attribute such as `altSecurityIdentities`.

Two requirements are security-relevant:

- **Ambiguity fails closed.** Zero matches denies; more than one match MUST deny loudly
  rather than selecting the first. Two users matching one certificate is an impersonation
  path.
- **Weak mappings MUST be issuer-pinned.** Matching on email or CN alone binds to a *name*
  rather than to a key, so a certificate from any other trusted CA bearing the same subject
  impersonates that user. Either use a strong mapping (issuer plus serial, or a SID
  extension), or verify the issuer alongside the searchable attribute. Weak mappings
  require explicit opt-in.

### Machine identity

Two supported mechanisms, in preference order:

1. **Kubernetes projected ServiceAccount token** (primary). The workload requests a token
   with an audience of `port49`; the kubelet writes and rotates it automatically. The
   broker validates it against the cluster's published JWKS and derives the identity
   `system:serviceaccount:<namespace>:<name>`. No CA, no certificate distribution, no
   rotation to implement, and no secret at rest.

2. **Issued workload certificate** (static hosts). Reuses the broker's existing
   certificate validation path with a separate trust anchor. The workload renews its own
   certificate ahead of expiry; only initial enrollment is manual.

SPIFFE/SPIRE is a viable third option for heterogeneous fleets but is **not** required and
is not a v1 dependency.

### Trust domain separation

Human and machine identities MUST be unforgeably distinct in the policy engine. A workload
identity MUST NOT be able to present as, or inherit the grants of, a human principal. This
is a small amount of code carrying a large share of the security value.

## 8. Token model

### Two credentials, two lifetimes

| | Lifetime | Location | Operator cost |
|---|---|---|---|
| **Session** | 8–16h | agent, local only, never on the wire | one certificate authentication per day |
| **Device token** | 30–600s, single-use | transient | none — minted automatically |

A single credential is not sufficient. One long-lived credential pasted into devices is a
password with an expiry date; one credential per authentication with no session forces a
certificate interaction per device.

### Token format: opaque handle

```
p49_7K2QF9XMRAVTC4EJHN6PBZ3D8W        (~30 characters)
```

The handle is a random secret, and all meaningful state lives in the store:

```
identity   principal derived from the certificate or workload token
groups     resolved from the directory at mint time
nas        the single device this token is valid for
```

**The store is keyed on `(nas, username)`, not on the handle value.** This is required for
CHAP. In a CHAP exchange the daemon never receives the token — it receives
`MD5(id ‖ secret ‖ challenge)` and must compute the same digest from the *plaintext* to
compare. A store keyed by handle value cannot be queried without the value, which would
make CHAP unimplementable while §14 requires it to be tested. Keying on `(nas, username)`
lets the daemon fetch the small candidate set for that user on that device and verify each.
Device binding becomes structural rather than a post-lookup comparison, and the handle
reverts to being purely a guessing-resistance secret.

A principal may hold several concurrent tokens for one device (see batch minting, §16), so
the store operation is **atomic match-and-delete within a keyed set**, not a plain
get-and-delete. §12's store interface reflects this.

**Rationale for an opaque handle over a self-describing signed token:**

- **Single-use enforcement is free.** A match-and-delete answers "has this been spent?"
  with the same operation that reads it — no separate replay-prevention store, no race
  between replicas. A signed token would require a nonce store to achieve the same
  property, making the "stateless" option strictly more complex.
- **Length.** TACACS+ field limits differ by authentication type (PAP's data field is
  materially tighter than ASCII login's — exact limits to be confirmed against RFC 8907
  §4), and devices impose their own input limits. A signed payload carrying identity,
  groups, NAS, expiry and signature would exceed safe bounds. 30 characters does not.
- **Revocation is immediate.** Deleting the key ends it. A signed token is valid until
  expiry regardless of any action taken.

### Single-use means single-session, not single-packet

A strict delete-on-read design fails on the first retransmission. Devices retry: a TCP
reset between the daemon's read and its REPLY, a slow store crossing the device's timeout,
or the two independent server groups §13 *requires* all produce a second attempt with the
same token. Under delete-on-read that retry finds nothing, and the practical result is a
flaky login rather than a security property.

On redemption the daemon therefore replaces the token with a short-lived **receipt** bound
to `(nas, port, user)` carrying the decision. An identical retry within the receipt window
(~30s) replays the stored decision. Anything else — a different device, a different line —
finds no receipt and is rejected. The receipt is what makes device-mismatch rejection the
high-signal detection event described below, rather than an event that also fires on
ordinary packet loss.

### Expiry is enforced by the store

The broker writes with a **relative TTL**; the daemon performs an atomic match-and-delete.
Presence means valid; absence means expired or spent. Neither component writes or compares
a timestamp.

This removes clock synchronization as a *correctness* dependency — broker and daemon clocks
may disagree without producing an incorrect accept or reject. NTP remains necessary for
certificate validity checking and audit correlation, but is no longer a security
dependency of the token path. This is particularly important for multi-region deployments,
where components sit in different NTP domains.

### Device binding

Every token is scoped to exactly one device. The daemon rejects a token presented from any
other source address. Combined with single-use and a short TTL, a captured token requires
an attacker to replay it against the specific device it was cut for, before legitimate use
consumes it. Rejection on device mismatch is a high-signal detection event — it does not
fire during normal operation.

### Username binding

The daemon MUST verify that the username presented at the device matches the principal the
token was minted for. Without this the token is a bearer credential for whatever name the
attacker types, and accounting attributes the session to the wrong human.

### Escalation credentials

`enable` is a separate authentication — usually on a new connection, with
`authen_service=ENABLE` and, on many platforms, a username of `$enab15$` rather than the
principal. No token exists for it, because the operator is already logged in and typing
interactively.

port49 therefore mints a **pair**: a login token and an enable token, both device-bound,
both single-use, sharing a TTL. Every relevant automation tool already has a second
credential field — `enable:` in Oxidized, `secret=` in Netmiko — so the pair drops into
existing configuration unchanged. Subjects that should not escalate are configured with no
enable mechanism and are refused.

Because the enable exchange does not carry the principal's username, **session context is
keyed on `(nas, port)`**, with the username as a verified attribute rather than part of the
key. Accounting attributes the escalation to the real principal regardless of what the wire
said. Mechanisms and ceilings are specified in the policy engine spec, §7.

### Per-account TTL

Token TTL is a **policy attribute of the account**, not a global constant. An interactive
login needs ~60s, because mint and use are one SSH handshake apart. A batch job walking
thousands of devices needs a window matching the run.

Lengthening the TTL is a bounded concession: the token remains single-use and device-bound,
so a longer window widens replay opportunity on an *unspent* token only. Because it lives
in policy, the value is visible in review alongside the grants it accompanies.

## 9. Authorization model

> The engine is specified in full in
> [`2026-08-23-policy-engine-spec.md`](2026-08-23-policy-engine-spec.md). This section
> covers the shape and the reasoning; that document covers the grammar, evaluation order,
> schema, and platform behavior.

### Concepts

Templates do not compose, and they conflate *what* a principal may do with *where*. A
large fraction of apparently bespoke authorization profiles are in fact the same
permissions applied to a different device set. Separating the two collapses that
combinatorial growth.

| Concept | Answers | Authored by |
|---|---|---|
| **Device** | Which NASes may connect, what vendor, where, with what key | imported or generated |
| **Platform** | How to speak a vendor's dialect | port49 ships it |
| **Scope** | Which devices a rule covers | operator |
| **Principal** | Who actually walked in the door | nobody — runtime |
| **Subject** | Which principals a rule applies to | operator |
| **Role** | Which commands | operator |
| **Privilege level** | What the device is told at login | operator names, port49 renders |
| **Grant** | Subject × scope × roles × level × expiry | operator |

Three of these carry most of the weight:

**Device is a fact; Scope is a selector.** Inventory is imported and describes reality;
scopes are authored and describe intent. Without that split, `match: {site: us_west}` has
nothing behind it — TACACS+ gives the daemon a source address and nothing more, so device
attributes must come from an inventory (§10).

**Principal is runtime; Subject is policy.** A subject addresses a *set* of principals and
takes exactly two forms — an LDAP group, or a literal identity. One mechanism therefore
covers both directory-driven human access and hand-maintained service accounts, which are
otherwise two separate configuration systems.

**Privilege decides what the device will offer; the role decides what port49 will permit
within it.** These are not independent axes — the effective permission set is the
intersection, and the role is always a subset. A backup account needs `admin` privilege so
`show running-config` is *reachable*, while command rules confine it to `show`.

When port49 is unreachable, the device-local role the privilege level names is the policy
that remains. The role is what you get while port49 is watching; the privilege is what you
get when it is not. The device-local role must therefore be chosen as a sane approximation
of the port49 role, not as a formality.

```yaml
roles:
  - name: read_only
    privilege: readonly
    permit: [show **]

  - name: bgp_operator
    privilege: operator
    permit: [show bgp **, clear bgp /^[0-9]+$/ **]
    deny:   [clear bgp all]

scopes:
  - {name: us_west_edge, match: {site: us_west, role: edge}}
  - {name: all_devices,  match: {}}

subjects:
  - name: svc_bgp_automation
    identity: "system:serviceaccount:netops:bgp-automation"
    token_ttl: 120s
    enable: none

grants:
  - {subject: svc_bgp_automation, scope: all_devices,  roles: [read_only]}
  - {subject: svc_bgp_automation, scope: us_west_edge, roles: [bgp_operator],
     expires: 2026-12-01}
```

### Matching is structural, not textual

Rules match the **argument vector** the device actually sends — `cmd=show`,
`cmd-arg=bgp`, `cmd-arg=summary` — rather than a string reconstructed from it.
Reconstruction is lossy: the mandatory/optional flag is discarded, embedded whitespace
becomes indistinguishable from argument boundaries, and distinct requests collapse to the
same string. Rules match the full vector unless they end in `**`, so there is no
accidental substring match. Regex is available, confined to a single argument position.

This is not only a safety property. §9's own tooling requirement — that CI render *which
commands* a change adds or removes — is not computable over arbitrary regex. Choosing an
enumerable matching language is what makes the effective-permission diff real rather than
aspirational.

**Resolution is most-specific-wins**, compared position by position, with ties going to deny.
There is exactly one deny mechanism. A global deny-wins rule is simpler to state but cannot
express an exception without negation, and RE2 has no lookahead — so a broad deny added under
pressure has no safe way to be narrowed. Because specificity is a property of the rule rather
than its position, evaluation remains order-independent and the diff remains exact. The
guarantee that deny-overrides would have offered is replaced by visibility: CI reports every
shadowed deny and the permit that beats it.

**Entity names are classified, not canonicalized.** `deny: interface @management` means the
same thing on EOS, NX-OS, and Junos because each adapter declares which of *its* names belong
to the class. A rule referencing an undefined class fails at load, so the silent non-match —
a deny that quietly stops applying on the vendor nobody updated the regex for — cannot happen.

### Expiring grants

Grants MAY carry an `expires` date. Service accounts and temporary elevations otherwise
accumulate indefinitely. An expiry field with automated reminders makes temporary access
actually temporary and turns access review into a report rather than an investigation.

### Three evaluation points

| Point | Question | Data source |
|---|---|---|
| **Mint** (broker) | May this identity reach this device? | directory groups + scopes + inventory |
| **Session** (daemon) | What shell profile does this login get? | session context |
| **Per command** (daemon) | May this identity run this command here? | session context |

The middle point is the `service=shell` authorization with an empty `cmd`, which returns
`priv-lvl`, `shell:roles`, `local-user-name`, `idletime` and similar. It is where a large
share of deployed TACACS+ does *all* of its authorization — platforms such as Junos have no
meaningful per-command path — so it cannot be an afterthought. Vendor attributes are
rendered by the broker at mint from the device's platform and written into session context,
so the daemon returns a precomputed list and never learns what a platform is.

Evaluating device scope at mint time means an unauthorized target fails **before the
connection is opened**, rather than after login with a per-command denial.

### Session context

TACACS+ authorization requests carry a username but no token, and continue for the life of
a device login. The daemon therefore retains the resolved identity, the effective rule set,
and the rendered vendor attributes, keyed on **`(nas, port)`**.

The key deliberately excludes the username. The `enable` exchange arrives as a separate
authentication whose username is frequently `$enab15$` rather than the principal, so a key
containing the username cannot resolve it. The username is stored as a verified attribute
of the context instead.

**Session context MUST live in the shared store, not in process memory.** TACACS+ commonly
opens a new TCP connection per transaction, so authentication and subsequent authorization
requests may be served by different replicas.

**Refresh policy.** Session context carries a short TTL (~5 minutes) and is refreshed from
the directory by the broker while the login remains active. Refresh MUST be
**refresh-ahead**: serve the cached value immediately and refresh in the background.
Synchronous refresh would place directory latency directly on the command path.

The cost is that a revoked principal may complete one additional command during the
refresh window — widening the revocation window by tens of milliseconds against a
five-minute refresh interval. The benefit is that per-command authorization is always a
single store lookup.

**Directory unavailable.** Serve stale context up to a hard staleness ceiling, alarming
throughout, then fail closed. The ceiling is a security parameter and MUST be explicit
configuration. Revocation does not function during the grace window; this trade must be
documented rather than left to operator judgment during an incident.

### Tooling requirements

Policy is only reviewable if reviewers can see what changed in effect, not in text.

- **Effective-permission diff.** CI MUST render the effective change of a policy
  modification: which commands, on how many devices, added or removed. This requirement is
  what forces an enumerable matching language; it is not computable over arbitrary regex.
- **`port49 explain`.** Resolve a hypothetical decision and report the reason, including
  which role would grant a denied command. This is what allows requesters to self-serve
  rather than escalating. Where a control cannot be enforced on the target platform,
  `explain` MUST say so rather than reporting a decision the device will not honor.
- **Policy tests.** Assertions stored alongside policy and executed in CI against a
  file-backed inventory:

```yaml
tests:
  - {subject: svc_config_backup, device: dev-01, command: "show run",  expect: permit}
  - {subject: svc_config_backup, device: dev-01, command: "configure", expect: deny}
```

- **`port49 devices capabilities`.** Report, per device, what its platform is capable of
  authorizing against what it has been observed to authorize. A device with
  `aaa authorization config-commands` disabled looks entirely healthy while every
  configuration line goes unauthorized and unaccounted; this is the report that surfaces it.
  Operators MUST never be asked to assert device behavior the system can observe.

Policy tests are what make role refactoring safe, and are not achievable with rendered
templates.

## 10. External data sources

Two external systems feed the broker: the **directory**, which supplies group membership
for principals, and the **device inventory**, which supplies facts about devices. Neither
sits on the authentication hot path.

### Directory

The directory supplies **group membership only**. Entitlement semantics live in port49
policy under version control. This separation allows policy to be reviewed, tested, and
reverted without a directory change.

### Server pool

```yaml
directory:
  servers:
    - { uri: "ldaps://dc-01.corp.example.com", priority: 100, site: us-west }
    - { uri: "ldaps://dc-02.corp.example.com", priority:  90, site: us-west }
    - { uri: "ldaps://dc-03.corp.example.com", priority:  50, site: us-east }
  health_check:    { interval: 30s, timeout: 2s }
  circuit_breaker: { failure_threshold: 3, probe_interval: 60s }
  failback:        { stability_window: 5m }
```

- **Priority ordering** with failover to the next healthy server.
- **Health checking and circuit breaking**, so an unavailable server is skipped rather than
  retried on every request.
- **Sticky selection** — remain on the selected server rather than re-evaluating per query.
  Round-robin across replicas at different replication stages produces membership that
  appears to flap.
- **Failback hysteresis** — require sustained health before returning to a higher-priority
  server.
- **Site awareness.** All servers in the local site SHOULD be exhausted before crossing to
  another site. Inter-site directory replication may lag by many minutes, so failing to a
  remote site can move membership backward in time. Site crossings MUST be logged as
  consistency events.
- **Per-deployment locality.** The broker SHOULD derive its own site from the environment
  and sort `same-site-first, then priority`, so one configuration serves all regions
  without drift.

### Pre-warming

The broker SHOULD resolve group membership for the full operator population on a schedule
(hourly is sufficient), independent of activity.

Without pre-warming, the grace window protects only principals already active — a person
arriving during a directory outage has no cached membership and is denied. The dataset is
small (hundreds of principals), making this a cheap way to extend grace coverage to the
whole population.

### Replication lag

Effective revocation latency is `refresh interval + directory replication lag`. Quorum
across multiple servers is explicitly **rejected**: a majority vote on a partially
replicated removal reports the principal as still a member, making revocation slower, and
requiring agreement reduces availability relative to accepting any healthy server's answer.
Sticky selection with priority ordering provides a consistent view, which is the property
actually needed.

### Device inventory

TACACS+ carries no device identity — the daemon observes a source address and nothing else.
Every device attribute the design depends on (`site`, `role`, and critically `platform`)
therefore comes from an inventory, and the shared secret each NAS uses comes from the same
place. Inventory is specified in the policy engine spec, §10; three properties belong here
because they are architectural:

**Inventory is a snapshot, never a live query.** A separate component — the inventory
service (§6) — runs connectors against NetBox or Nautobot on a schedule and publishes a
versioned snapshot that the broker and daemon pull and cache. Querying a source of truth
synchronously at mint would put it on the authentication path, which is the same mistake §6
exists to prevent for the directory. Isolating the connectors in their own workload also
keeps source-of-truth credentials in one place and prevents a faulty third-party connector
from reaching the authentication path at all.

**Admission splits from inventory.** The address list is not the security boundary — the
shared key is, since a device connecting without the right key sends unreadable data.
Existence therefore comes from the source of truth, while *key assignment* stays in the
policy repository under review. The fleet is maintained once; the admission decision is still
a pull request.

**Change per sync is bounded.** A sync that would remove more than a configured share of
the fleet refuses, retains the last good snapshot, and alarms. A half-available SoT or a
mistyped filter would otherwise silently deauthorize the fleet.

**Source-of-truth write access is privilege-granting.** If scopes match on synced
attributes, whoever can change a device's role in NetBox can move it into or out of a
scope, with no policy change and no diff. Scope-membership changes MUST therefore appear in
the sync diff, scopes MUST be able to pin device sets explicitly, and SoT write access MUST
be documented as privileged. The governing rule is that the source of truth supplies facts
about devices while the policy repository supplies intent — the moment an SoT tag can grant
a permission, authorization has left code review.

## 11. Protocol support

| RFC | Port | Status |
|---|---|---|
| **RFC 8907** — TACACS+ | 49 | Primary. The transport all deployed devices use. |
| **RFC 9887** — TACACS+ over TLS 1.3 | 300 | Implemented to spec, forward compatibility. |

Both listeners MUST be independently configurable and MUST be separable, per RFC 9887's
requirement that TLS and non-TLS services be distinct to prevent downgrade attacks.

RFC 9887 is implemented for standards correctness and future device support. **The product
does not depend on it**, because certificate identity is delivered through the RFC 8907
path.

## 12. Failure model

`✓` works · `⚠` degraded · `✗` fails

| Failure | New session | New device login | **Active login (commands)** | Batch run in progress |
|---|---|---|---|---|
| **Directory unavailable** | ✓ certificate only | ⚠ ok within grace; else denied | ✓ stale context to ceiling | ⚠ as new login |
| **Token store unavailable** | ✗ | ✗ | ✗ → device falls back to local authorization | ✗ |
| **Broker unavailable** | ✗ | ✗ | ✓ **unaffected** | ✗ |
| **All daemons unavailable** | ✓ | ✗ → device-local break-glass | ⚠ device retains its shell profile; remote authorization stops | ✗ |
| **One region unavailable** | ✓ | ✓ device fails over | ✓ | ✓ |
| **Device→daemon partition** | ✓ | ✗ → break-glass | ⚠ as above | ✗ |
| **Operator credential lost** | ✗ | ✗ | ✓ existing logins persist | ✗ |
| **Inventory service unavailable** | ✓ | ✓ last good snapshot | ✓ | ✓ |

### Consequences

**Broker/daemon failure independence is a required property.** Broker unavailable means no
new access while everyone currently working continues. This is the correct degradation
shape for network AAA, and it holds only while the daemon never calls the broker
synchronously.

**The token store is the critical dependency.** It is the only failure that breaks the
active-login column. Mitigations:

- **Hard timeouts** (~50ms) on all store operations. A slow store must fail fast rather
  than hang; queued requests are worse than rejected ones.
- **Circuit breaker** — after repeated timeouts, stop calling the store, serve from local
  cache, and probe periodically.
- **Per-replica read-through cache for session contexts.** These tolerate staleness by
  design. Token redemption MUST NOT be cached — it is the single-use authority.
- **Connection pool separation** between token operations and session-context reads, so
  mint pressure cannot starve authorization.

This produces the correct degradation under a slow store: **new logins fail fast while
active sessions continue.**

**Store health MUST NOT be wired into the readiness probe.** If all replicas become
unready simultaneously, the service loses all endpoints, devices declare the server dead,
and a degraded store becomes a total AAA outage. Serve from cache and alarm instead.

**Device-side AAA configuration is part of the failure model.** When TACACS+ servers are
declared dead, device behavior — retaining an existing shell profile while remote
authorization ceases — determines the outcome for logged-in operators. port49 MUST ship
tested reference AAA configuration per platform.

### Store interface

The store is accessed through a narrow interface:

- set-with-TTL, into a keyed set
- **atomic match-and-delete within a keyed set**
- short-lived receipt write and read
- session context read/write

**Requirement:** the store MUST provide atomic match-and-delete with TTL, and MUST be
reachable from every daemon a given device can reach. Topology is a deployment choice
(§13).

Match-and-delete rather than get-and-delete because tokens are keyed on `(nas, username)`
to make CHAP implementable (§8), and one principal may hold several concurrent tokens for a
device. The daemon fetches that candidate set and atomically removes the one that verifies.

A narrow interface makes the store pluggable (Redis, Valkey, DynamoDB, etcd, or an RDBMS)
rather than mandating one dependency, and permits an **in-memory implementation** so the
daemon can be integration-tested as a single binary with no external services.

## 13. Deployment requirements

Stated as requirements. Concrete topology is an operator concern and belongs in a
deployment guide.

**Source address visibility (critical).** TACACS+ carries no device identity in the
protocol; the server infers it from the TCP source address. Deployments **MUST NOT** apply
SNAT to device traffic, and the daemon **MUST** observe the true client source address.
A source-rewriting load balancer silently disables device binding — the check continues to
run but no longer means anything.

**Token store topology.** Because the mint follows the operator or workload while
redemption follows the device, the two may occur in different locations. Options:

| Topology | Trade |
|---|---|
| **Single global store** (recommended default) | Always correct. Cross-region latency on redemption only, once per login. |
| Regional stores + mint routed by target device region | Lowest latency. **Fails during regional failover**, when redundancy is most needed. |
| Regional stores with replication | Survives failover. Single-use enforced per-region, yielding a narrow replay window. |

**Independently upgradeable server groups.** Deployments SHOULD present two server groups
that are independently deployed and independently upgraded, with devices configured to use
both. Network-layer failover cannot detect a build that passes health checks but fails
authentication; only workload separation with staggered rollout protects against
correlated software failure. Two addresses in front of one workload provide no such
protection.

**Replica separation.** Pod anti-affinity and topology spread constraints are sufficient
for node and zone separation. Dedicated node pools are unnecessary absent a specific
hardware or compliance requirement.

**Connection handling.** Graceful termination with connection draining; a disruption budget
sufficient to preserve regional capacity during maintenance. Autoscaling SHOULD key on
connection count rather than CPU — the workload is I/O bound.

**Anycast note.** Anycast addressing gives automatic failover but interacts poorly with
long-lived TCP: a route change mid-connection lands packets on a server with no state for
that session. Deployments using anycast SHOULD prefer connection-per-transaction over
TACACS+ single-connection mode, trading cache locality for resilience to route changes.

## 14. Testing strategy

Integration testing uses **containerlab** with real network operating system images. The
single-dependency daemon design plus an in-memory store implementation makes these
topologies cheap to construct.

Required assertions:

- Full authentication flow against real devices, per platform and per authentication type
  (ASCII, PAP, CHAP).
- **Token minted for device A is rejected when presented from device B.** This passes
  trivially in a lab with direct connections and would regress the moment a source-
  rewriting proxy is introduced — it must be asserted explicitly.
- Single-use enforcement: a replayed token is rejected.
- **Retransmission is not a replay.** An identical retry within the receipt window succeeds;
  the same token from a different device or line is rejected.
- Expiry: a token presented after its TTL is rejected.
- **Session authorization returns the correct vendor attributes per platform**, with
  mandatory versus optional flags honored. A mandatory attribute the platform cannot parse
  causes the device to reject the session outright, so this must be caught in the lab.
- **`enable` works** for all configured mechanisms, including the `$enab15$` username path
  resolving through session context keyed on `(nas, port)`.
- Per-command authorization decisions match the policy test suite.
- **Config-command authorization is detected**: a device with `aaa authorization
  config-commands` disabled is identified and reported rather than appearing healthy.
- Every row of the failure matrix (§12): directory unavailable, store unavailable, store
  slow, broker unavailable, daemon unavailable, partition.
- Sustained load at the design target rate (§5).
- Device AAA fallback behavior per platform when servers are declared dead.

The policy engine spec, §14, lists the matcher-level assertions that do not require a
device image.

## 15. Language: Go

**Decision: Go.**

- **Performance requirements are modest.** The design target is dominated by store and
  directory round-trips, not computation. Go has substantial headroom; the argument for a
  systems language would apply to a line-rate packet processor, which this is not.
- **Ecosystem fit.** Mature, well-maintained libraries for Kubernetes, LDAP, Redis, and
  TLS. The alternatives' equivalents are less developed for exactly these dependencies.
- **Contributors.** This project's viability depends on adoption by network engineers,
  for whom Go is the lingua franca of the surrounding ecosystem (Kubernetes, Prometheus
  exporters, containerlab). A less accessible language would materially shrink the
  contributor pool.
- **Concurrency model** fits connection-per-transaction TCP with many short-lived handlers.
- **Single static binary** with straightforward cross-compilation, which matters for the
  CLI distributed to operator workstations.

**Argument against:** the TACACS+ parser consumes untrusted binary input, where stronger
memory-safety guarantees have real value. Go is memory-safe; the realistic residual risk is
logic error in the parser, addressed by fuzzing in either language. Not sufficient to
outweigh the ecosystem and contributor considerations.

## 16. Client libraries

The **CLI is the universal client** — anything able to execute a subprocess is integrated.

| Artifact | Scope | Priority |
|---|---|---|
| `port49` CLI | login, token, explain, test, SSH integration, agent | v1 — primary effort |
| Python library | read identity, mint, batch, retry (~300 lines) | v1 |
| Ansible lookup plugin | thin wrapper over the Python library | v1 |
| Go library | falls out of the daemon implementation | opportunistic |

The **HTTP API is the product; libraries are conveniences.** Every language binding is a
permanent maintenance obligation. A documented endpoint that can be called in a few lines
lets the ecosystem supply the rest.

Machine workloads require no agent: identity is a file and minting is a single request.
Only interactive human use requires session management and SSH integration.

### Integration examples

```python
# Netmiko / Python
conn = ConnectHandler(device_type="arista_eos", host=device,
                      username="svc-script-exporter",
                      password=port49.token(device))
```

```bash
# Shell / SSH
sshpass -p "$(port49 token "$DEVICE")" ssh admin@"$DEVICE" "show running-config"
```

```yaml
# Ansible
ansible_password: "{{ lookup('port49', inventory_hostname) }}"
```

**Batch minting.** A sweep across thousands of devices SHOULD be able to request many
handles in a single call. Sequential minting adds prohibitive overhead to backup and
compliance runs.

## 17. Open questions

1. **License.** To be selected before the repository is made public. Apache-2.0 is the
   likely choice for explicit patent grant and corporate adoption.
2. **Token store topology.** Global versus regional (§13) — a deployment decision, but the
   recommended default should be validated under load.
3. **Single-connection mode versus anycast.** Cache locality against resilience to route
   changes (§13). Requires measurement.
4. **Exact TACACS+ field length limits** per authentication type, confirmed against
   RFC 8907 §4, to bound token handle length definitively.
5. **Unattended automation.** Where automation is operator-initiated, the operator's own
   identity is correct and sufficient. Genuinely unattended workloads require the machine
   identity path (§7) — the relative volume of each should inform sequencing.
6. **Session context refresh cost** at the design target: active session count times
   refresh frequency against directory capacity.
7. **Engine decisions.** The six open at first draft are now resolved, with reasoning
   recorded in the policy engine spec, §13. Three smaller questions remain open there:
   ordered version comparison across vendor version strings, inventory-sourced entity
   classes, and which projection rule shapes can be proven equivalent per platform.
