    Install with Helm¶

    Run the commands from the repository root. You need a cluster, kubectl and helm, and a namespace for the release (the examples use port49).

    1. Create the Secrets¶

    Make the device key and the sealing key as yourself, in the current directory. Neither needs root, and the sealing command also writes a broker-encryption.key that this chart does not use:

    port49d key device core_v1 --dir . --device-owner "$(id -un)" --device-group "$(id -gn)"
port49d key sealing --dir . --daemon-user "$(id -un)" --broker-user "$(id -un)"

    Create each Secret with --from-file, never --from-literal, so no secret reaches a shell history or a process list:

    kubectl -n port49 create secret generic port49-device-keys --from-file=core_v1=./core_v1
kubectl -n port49 create secret generic port49-encryption --from-file=encryption.key=./encryption.key
kubectl -n port49 create secret generic port49-etcd-ca --from-file=ca.crt=./etcd-ca.crt
kubectl -n port49 create secret generic port49-etcd-port49d --from-file=tls.crt=./port49d.crt --from-file=tls.key=./port49d.key
kubectl -n port49 create secret generic port49-etcd-broker --from-file=tls.crt=./broker-etcd.crt --from-file=tls.key=./broker-etcd.key
kubectl -n port49 create secret generic port49-broker-tls --from-file=tls.crt=./broker.crt --from-file=tls.key=./broker.key --from-file=ca.crt=./client-ca.crt

    The device keys Secret holds one key per version, named <ref>_v<N> in the policy. The encryption key is 32 bytes, the same in both pods. To check, run kubectl -n port49 get secret. All six are listed.

    To sync the device keys from Vault instead, use examples/external-secret.yaml: one Secret key per version (core_v1, core_v2), each from its own remote key, so adding a version adds a remote key and an entry.

    A ClusterSecretStore can be read from every namespace

    The example's store is a namespaced SecretStore, usable only from the release's namespace. A cluster-wide ClusterSecretStore without conditions lets anyone who can create an ExternalSecret anywhere read the device keys through your Vault role. examples/external-secret-clusterstore.yaml shows the option, with the namespace named.

    2. Bring up etcd¶

    port49 does not create or run etcd. examples/etcd/ is a three-member example (the kind smoke runs it with its init Job). port49 needs three members, etcd 3.4.24, 3.5.8 or 3.6 or later, and its own cluster.

    etcd's disk

    etcd needs sustained WAL fsync p99 under 10 ms. See Requirements.

    To check, run kubectl -n port49-etcd get pods. All three members are Ready.

    3. Apply port49's etcd roles¶

    Make the roles script from your two configs. Use local copies of both, taken from the port49d.yaml and port49-broker.yaml keys of the chart's two config ConfigMaps in helm template output, with the broker's etcd cert_file and key_file pointing at port49-etcd-broker's own tls.crt and tls.key, because store-roles refuses two components with one CN:

    port49d store-roles --config port49d.yaml --broker-config port49-broker.yaml > roles.sh
kubectl -n port49-etcd create configmap port49-etcd-roles --from-file=roles.sh
kubectl -n port49-etcd apply -f deploy/helm/port49/examples/etcd/etcd-init-job.yaml

    The Job applies the output as etcd's root and enables auth. Its header comment says which Secrets it needs. To check, run kubectl -n port49-etcd wait --for=condition=complete job/etcd-init --timeout=300s. The Job completes.

    4. Install the chart¶

    helm install port49 deploy/helm/port49 -n port49 \
  --set keys.existingSecret=port49-device-keys \
  --set encryption.existingSecret=port49-encryption \
  --set etcd.caSecret=port49-etcd-ca \
  --set etcd.port49d.existingSecret=port49-etcd-port49d \
  --set etcd.broker.existingSecret=port49-etcd-broker \
  --set broker.tls.existingSecret=port49-broker-tls \
  --set 'etcd.endpoints={https://etcd-0:2379,https://etcd-1:2379,https://etcd-2:2379}' \
  --set-file policy=policy.yaml --set-file inventory=inventory.yaml

    Four values are required:

    1. etcd.endpoints: every member, at least three. The schema refuses fewer, a repeated or non-https member, and an empty Secret name. A client given one URL has no failover.
    2. keys.existingSecret: mounted whole at /run/port49/keys, in port49d's pod only, mode 0440 under fsGroup (measured on kind: L82).
    3. encryption.existingSecret and encryption.id: mounted in both pods.
    4. policy and inventory, with --set-file. Without a policy port49d refuses to start.

    The release namespace must enforce Pod Security baseline. The volume setup's root init container uses CHOWN, FOWNER and FSETID only, all in baseline's list. A namespace enforcing restricted refuses it, so no pod is created. To label the namespace, run:

    kubectl label --overwrite ns port49 pod-security.kubernetes.io/enforce=baseline

    Then pick the sign-in backend.

    Add -f deploy/helm/port49/examples/values-issuance.yaml to the install, with the issuer, client and domain replaced. The values replace the chart's humans list, so keep the x509 entry in it if people also sign in with client certificates, or the broker stops accepting them. OIDC sign-in has the block.

    The chart trusts ca.crt from broker.tls.existingSecret for client certificates and asks each certificate's own OCSP responder. If your CA has none, set crls: under config.broker.broker.certificate_status before the first sign-in. Client certificates has the block.

    Directory password and The directory have the blocks and the Helm values.

    To check, run:

    kubectl -n port49 get pods
kubectl -n port49 port-forward <release>-port49d-0 9049:9049 &
curl -fsS 127.0.0.1:9049/readyz

    Every pod is Ready and /readyz prints serving. A schema refusal names the value at fault before anything is created.

    5. The issuing CA¶

    Only when issuance is on (the OIDC and directory password tabs turn it on). It needs -f examples/values-issuance.yaml first, so that broker.identity.issuance is set: init-issuer refuses a broker without it. Every broker must hold the same issuing CA, or it refuses to start against the store's record of it. After the first install run, once:

    deploy/helm/port49/scripts/copy-issuer.sh port49 port49 --from 0

    --from names the broker whose CA is the one to keep. If no broker holds a CA, the script makes one in a one-shot pod. It copies the CA to each other broker, refuses to overwrite a different one (naming both sha256s), restarts the brokers and prints each pod's issuing as log line.

    To check, compare those lines. The (sha256:...) fingerprint is the same on every broker.

    A broker whose volume was lost gets its CA from one that has it, never from init-issuer:

    deploy/helm/port49/scripts/copy-issuer.sh port49 port49 --from 1 --to 0

    Do not run forget-issuer

    It removes the store's record of the CA, and every certificate issued under the old CA stops working. It is for the case where every broker lost the CA and no copy exists. The command is port49-broker forget-issuer --current sha256:<fingerprint>, with the fingerprint a broker's start line prints, and a record that holds a different CA is kept. After it, run init-issuer on one broker and copy the CA to the others. Stop every broker on the store before starting one on another CA.

    6. Create the enrollment store¶

    Only for directory password sign-in. Adapt the names in examples/init-enrollments-job.yaml to your values, then run:

    kubectl -n port49 apply -f deploy/helm/port49/examples/init-enrollments-job.yaml
kubectl -n port49 wait --for=condition=complete job/port49-init-enrollments --timeout=300s

    The Job completes. A broker that is already running finds the new store within 30 seconds, and until then its sign-ins answer enrollment_store_lost.

    7. Expose port 49¶

    port49d admits a device by the address it sees, so the device's source address must reach it unrewritten. service.type defaults to LoadBalancer with externalTrafficPolicy: Local. Measured on kind (L39, kube-proxy in iptables mode, a device outside every node, a NodePort Service):

    Setting, and where the device dials Result
    Cluster, a node running the pod fails: the source port49d sees is a pod-network address
    Cluster, a node not running the pod fails: the source is that node's own address
    Local, a node running the pod works: port49d sees the device's own address
    Local, a node not running the pod times out, and port49d logs nothing

    Keep Local. Under Local, give devices the LoadBalancer address, not a node's address: a pod that moves leaves its old node answering nothing. MetalLB in BGP mode advertises the address only from nodes with a ready pod (L85 measured that). For an anycast address, set service.anycast.enabled: true and service.anycast.address. The chart then requires service.type: LoadBalancer, externalTrafficPolicy: Local and port49d.preStopSeconds of at least 15, and refuses anything else.

    Unmeasured

    A cloud load balancer has not been measured.

    To check, run a TACACS+ login from a device. port49d logs the device's own address, and the decision log holds a redeem record with verdict: permit.

    Optional steps¶

    The details of each are under Chart options in the chart README.

    • Autoscaling: autoscaling.enabled renders an HPA.
    • Alerts and scraping: prometheusRule.enabled: true.
    • TACACS+ over TLS: tlsListener.enabled, with TLS.
    • Several regions: Stores.
    • Backups: Backup and restore and Back up with Velero.
    • Issuer discovery: issuerDiscovery.enabled binds system:unauthenticated cluster-wide. Enable it in one release per cluster.
