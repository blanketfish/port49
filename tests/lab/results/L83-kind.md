# L83: Secret-store agents rendering port49d's keys (kind)

Platform: kind v0.29.0, node image kindest/node v1.33.1, on a GitHub-hosted ubuntu-24.04 runner (image
20261026.354.1, kernel 7.0.0-1017-azure, Docker 28.0.4). Vault chart 0.34.1 (app 2.0.4), injector 1.7.6,
Secrets Store CSI Vault provider 1.7.4, secrets-store-csi-driver 1.6.1. Measured 2026-10-31.

Capture pointer: GitHub Actions run 41155086403, attempt 1, artifact `lab-l83` (`l83-results.md`,
`l83-cells.json`). The first run (41142675001) reused one probe pod across configurations, so its second
configuration's stat rows were the first's; that is fixed (9d7e50da) and this note uses only this run.

## Observations

| Cell | Verdict | What was measured |
|---|---|---|
| a1 injector, `perms "0440"`, default agent user | FAIL | the agent is uid 100; the file is `100:65532 0440`; port49d crash-loops on the owner rule (as designed) |
| a2 injector, `agent-run-as-same-user: "true"` | PASS | the agent is uid 65532; the file is `65532:65532 0440`; both pods Ready, 0 restarts |
| b1 CSI driver, provider default file permission | FAIL | the file is `0:0 0644` in a `0:0 1777` directory; port49d crash-looped (5 restarts) though the probe as 65532 can read it |
| b2 CSI driver, `filePermission 0440` | FAIL | the file is `0:0 0440`; the probe as 65532 cannot read it; port49d crash-looped (6 restarts) |
| c-a2 injector, version added at the store | FAIL | a login keyed with version 2 passed after 41s, but the pod was replaced (new uid): the injector reads its annotations at admission, so a new version is a rollout, not a reload |
| c-a1, c-b1, c-b2 | N/A | the configuration did not pass its (a) or (b) cell |

Consequences, used by the chart README: Vault Agent (injector) may be named only with
`agent-run-as-same-user: "true"`, and a new key version is a pod rollout; the Secrets Store CSI driver is
not named for device keys (neither b cell passes, and driver 1.6.1 sets no `fsGroupPolicy`, so `fsGroup`
does not apply). b1's cause is not measured here: the harness records the layout and the crash loop, not
port49d's refusal line, so no cause is asserted for it.
