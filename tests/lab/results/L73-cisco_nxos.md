- port49d ran with tls_listener.handshake_timeout 30s (the default is 5s) for this platform, because the image's first run sent its client flight 5.00 s after the server's flight, as the 5s timeout fired; each connection line records "device's next data N s after the server's first data", the measured delay on that connection
- **operator fact:** NX-OS 10.6.2.F waits exactly 5.00 s after the server's first flight before it sends its own on every RFC 9887 connection: all 67 connections in this run's `*.tls.json` that have both a server flight and a device reply show 5.00 s (minimum and maximum), whatever port49d did. A login is five TACACS+ steps (redeem, authorize session, account, authorize command, account), each on its own connection, so it takes about 25 s. port49d's `tls_listener.handshake_timeout` must therefore be above 5s for this image; with the 5s default every handshake is timed out, and the first run's control login failed that way (`handshake_timeout`, no device alert). This run used 30s. The token login's version command was bounded at 150 s and the SSH dial at 90 s because of this delay.
- the decision log in the evidence omits the 10416 lab seed mint records (the lab method reseeds every lab principal every few seconds; each is a `mint` event with `auth.method` lab)
- port49d: `certificate_status: {disabled: true}` in every cell but (i)'s decline window (the status path is L72's), `malformed_backoff_base: 2s`, `session_attributes: the lab file's`; the device: `revocation-check none` on both trustpoints
- not measured here: SCEP, CMPv2, EST and ACME enrolment; whether NX-OS checks port49's revocation status
