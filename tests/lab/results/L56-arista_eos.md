## Claim

Port49-issued certificates end to end on Keycloak and one device (plan 9b), with the real port49 CLI: a broker started with broker.identity.issuance and no issuing CA says in /v1/config issuance.available: false, the CLI says before any sign-in that the broker cannot issue, its log names init-issuer, and after port49-broker init-issuer and a restart issues; port49 login --oidc --no-browser signs in through a scripted browser, asks the password, writes a 0600 key and its certificate, names the principal, starts the agent and refreshes once; port49 token mints and the device takes the token over SSH; port49 refresh extends the device session with no sign-in; port49 login after the agent stopped starts a new one with no sign-in and extends the device session; port49 login --sign-in at a terminal, the address pasted, issues a new certificate; an administrator's sign-out refuses the certificate's next mint in the broker's logout words and ends the agent, a port49 login over that certificate removes it, and a sign-in from the time the broker names works; with Keycloak stopped, port49 token, port49 refresh and a new agent over the held certificate work, and port49 login --sign-in says the provider did not answer and when the held certificate ends; no compact JWS, code or private key in the CLI's raw output or the agent's log (policy engine spec §15 L56; §13 decision 43).

## Observation

The CLI reaches Keycloak through a CONNECT proxy in the test (`l56Proxy`), since this host does not resolve keycloak.port49.lab; that is lab plumbing, not part of the claim. The CLI's raw output is checked for a compact JWS or any value the run registered as secret (the issued key's included) before it is scrubbed for this note; only the authorization URL's state, nonce and code_challenge are exempt, being printed by design. A device token must be `port49 token`'s whole stdout and is checked for everywhere else, other commands' output and the broker's and port49d's logs included.
