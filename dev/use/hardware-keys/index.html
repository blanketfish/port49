    Hardware keys¶

    A person's session key can live on a YubiKey instead of in a file, and a device's policy can require a touch on that key at login. Only the client build of port49 reads a YubiKey or a smartcard. The static build exits 2 on port49 hwkey and says it was built without PKCS#11 support, so install the client build and its PKCS#11 module (libykcs11) first.

    Two keys on one token¶

    A device that accepts hardware_key_touch needs two keys on the same YubiKey:

    Key Slot Policy Config key
    The session key, which signs the login and each refresh 9a, or 9e where a site keeps it PIN once, touch never issued_key
    The touch key, which signs a challenge from the broker for each device that asks 9c touch always touch_key

    The broker checks that both attestations chain to Yubico's roots and name the same device. A session key in a file or the TPM cannot satisfy it, and a policy that accepts only hardware_key_touch locks that person out. The keys are in the port49d (broker.identity.per_login_mfa) and client references.

    1. Check the key¶

    port49 hwkey status reads the token and reports. It opens no key with the PIN and writes nothing.

    port49 hwkey status                 # human lines
port49 hwkey status --json          # one JSON object, for a script
port49 hwkey status --module <path-to>/libykcs11.so --token 1

    To check, the output ends with ready. Its first line says which attestation roots it checks against:

    roots: from broker broker.example.com:8443
module: <path-to>/libykcs11.so.2 (found)
token: <masked label>
ok    session_slot
...
ready

    The roots are the broker's own, fetched over TLS and checked against the broker_ca in your config. The line is roots: from broker <host>, or roots: --roots <file> when --roots FILE names a file instead, which is for offline use and wins over the broker. --broker URL names a different broker to ask.

    Each line after is a check, ok or FAIL with a reason: session_slot, touch_slot, attestation_roots, session_attested, touch_attested, touch_policy, same_token, and, for status alone, config_issued_key, config_touch_key, issued_certificate, certificate_expiry and agent. The attestation checks are the broker's own code. A serial is always shown masked. The exit codes are in Client commands.

    The roots have their own messages, all exit 2, and each names the way out:

    • the broker <host> is unreachable, so the attestation roots could not be fetched: retry, or pass --roots FILE: the broker did not answer, which says nothing about the key.
    • the broker <host> did not present a certificate from the configured broker CA ...: check broker_ca, or pass --roots FILE: a trust failure, not an outage. Find out why before pointing --roots at any file.
    • no attestation roots: the broker <host> serves none ...: attestation_roots_file is not set on the broker, so it does not verify hardware_key_touch.

    A wrong --roots FILE can make status say ready for a key the broker will refuse, or the reverse. It cannot grant anything, because the broker applies its own roots. Take the file from the broker's administrator, not from the key.

    2. Set the key up¶

    port49 hwkey setup runs the same checks, and when all pass it writes issued_key and touch_key into your own config file and nothing else.

    port49 hwkey setup

    To check, run port49 hwkey status again and look for ready.

    • If issued_key or touch_key already names another key, setup shows both values and asks at a terminal. With no terminal it changes nothing and exits 1. A key from /etc/port49/config.yaml is reported, not edited.
    • When a check fails, it prints the commands to run. The key is made with ykman, which asks for the management key. port49 never asks for it and never runs ykman itself.
    # if 9a already holds a key, add its certificate (this replaces nothing):
ykman piv certificates generate --subject "CN=port49 9a" 9a port49-9a.pub.pem
# only if 9a holds no key, make one (this replaces any key already there):
ykman piv keys generate --algorithm ECCP256 --pin-policy ONCE --touch-policy NEVER 9a port49-9a.pub.pem

    Slot 9c prints the same with --touch-policy ALWAYS. libykcs11 lists a slot's key only with a certificate in it, so port49 cannot tell an empty slot from a key with no certificate and prints both lines, certificate first. Run the keys generate line only if the slot holds no key. - With more than one token present, setup lists them by number, model and masked label, exits 2, and wants --token N. A session key in the TPM, a file or the Secure Enclave is reported as not on a token.

    3. Log in with the key¶

    port49 login asks the key's PIN once, on the terminal, with echo off. The PIN is never on a command line, in the environment, or in a log. A wrong PIN is sent once and never retried. The message says fewer tries are left after the first wrong PIN and one try is left before the key locks after the second. A blocked PIN is unblocked with the PUK: ykman piv access unblock-pin.

    If the agent's connection drops, its reconnect is another use of the key and asks for the PIN or a touch again (the session). When a device asks for a touch, port49 token and port49 ssh say touch your key now and the token blinks. On the measured YubiKey an untouched request ended after 14.4 seconds with no touch within 15s; touch the key when it blinks and try again, the key stayed unlocked, no PIN try was spent, and a touch right after the timeout signed with no PIN.

    A wrong PIN typed anywhere on the machine logs the agent off the key

    A mistyped PIN in another process, such as a second terminal's port49 login, makes the token log the running agent's session off. The agent's next refresh says your key needs its PIN: run port49 login, and its status reads locked. This is intended behaviour, so log in again with port49 login. Never let a script try a PIN on a token that an agent holds: it logs the agent off each time and spends the token's tries.

    A lent key plus its PIN is the person's login

    The PIN is the only thing between whoever holds the key and port49 login as that person. Revoke the certificate or the principal as soon as a key is lent, lost or taken, and do not wait for the certificate to expire: see Administer: revocation.

    What has not been measured¶

    Unmeasured

    • port49 hwkey status and setup have not been run against a real YubiKey. How they behave there, and whether libykcs11 lists a slot's key when the slot holds no certificate, are unknown (L91, open). The ykman lines above are what the commands print: read ykman piv info before and after.
    • The touch timeout, the low-tries flags and the wrong-PIN behaviour were measured on one YubiKey 5C Nano FIPS, firmware 5.4.3, with libykcs11 2.7.2 (the lab note). Other tokens, firmware and libykcs11 versions are unknown (L60, open).
    • Also unknown under L60: whether a port49 login to the running agent puts it back on the key after a wrong PIN typed in another process, whether port49 token still mints on the held connection after it, what other processes using the token do to the agent, and whether parallel forks sharing one agent, such as Ansible workers, are asked for one touch or several when a device requires hardware_key_touch. The agent batches queued requests. A mint whose caller gave up after its batch was sent still happens and its token goes unused, so the person can revoke it. Run port49 ssh <device> once for such a device before a play.
    • On macOS, port49 accepts a PKCS#11 module the admin group can write, because Homebrew's prefix is group-writable by admin. The evidence is a CI run in which Homebrew's libykcs11.dylib was refused without the rule, and the hardware claims were measured on Linux. No register entry covers a YubiKey on a Mac, so whether a Homebrew Mac signs in end to end is unknown.
    • How the macOS Secure Enclave key store behaves on a Mac is unknown (L63, open). It is experimental and opt-in.
