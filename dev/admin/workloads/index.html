    Workloads¶

    A workload is a program that logs in to devices without a person: a configuration backup, a compliance check, a deployment job. It has an identity of its own, so its access is granted, logged and revoked apart from any person's.

    Identity Proof Principal Use it when Guide
    A workload certificate an x509 certificate with a SPIFFE ID in a URI SAN, from a CA you run spiffe://<trust domain>/<path> the job runs on a host you manage, such as a cron job or a backup server Oxidized and step-ca
    A Kubernetes service account token the pod's projected token, checked against the cluster's published keys system:serviceaccount:<namespace>:<name> the job runs in a cluster, and you want no CA and no secret at rest Kubernetes service accounts

    Neither is required. The concepts are on Identities and Trust domains. How a workload becomes a subject, and why it gets its own device login, is on Roles and grants. The workload anchor and the people's anchor must be in unrelated hierarchies, so that nothing a workload CA signs can be read as a person.

    Workload certificates and step-ca¶

    The host holds a certificate valid for a few hours, a renewal timer replaces it, and the broker verifies it against the CA you name in broker.identity.machines (port49d reference). The Oxidized guide uses step-ca and has the provisioner's step-ca-workload.tpl, the broker's verifier, enrolling, renewing and the bad-day table. Give each host its own provisioner, with the SPIFFE ID fixed in its template, so a host can only obtain its own name. For an immediate stop, use port49 revoke (Revocation) instead of waiting for the CA's CRL.

    The certificate must name the CA's CRL

    A certificate whose CRL distribution points do not name step-ca's CRL is refused certificate_status_unavailable (503) under the default on_unavailable: refuse; the guide's template adds the extension (L48).

    The workload directory¶

    By default a workload's groups come only from the policy: a subject names the SPIFFE ID in identity:. At fleet scale you can use a directory group instead, so that adding a host to cn=ci-runners grants it what the group has, with no policy edit. That is the machine_group: subject. It matches workloads only, takes no username: (the name comes from the entry) and never sits beside group: or identity: in one subject.

    subjects:
  - name: ci_runners
    machine_group: "cn=ci-runners,ou=groups,dc=example,dc=com"
  - name: svc_backup
    identity: ["spiffe://example.com/host/backup-01"]
    username: svc-backup

    port49 policy test reports group_subject for the first and workload_no_username for a subject with no username, which then mints only under broker.identity.machines[].directory (Roles and grants).

    Opting in¶

    The broker finds a workload's entry through a directory: block on the machine verifier. It is off until you write it, and all four keys are required:

    broker:
  identity:
    machines:
      - type: x509
        trust_anchor_file: /etc/port49/workload-ca.pem
        spiffe_trust_domains: ["example.com"]
        directory:
          kind: spiffe_id
          attribute: uid
          allow_weak: true
          issuers: ["CN=Example Workload CA,O=Example"]
    • kind: spiffe_id is the only kind. The entry holds the workload's SPIFFE ID in attribute.
    • attribute has no default, and the config refuses the attribute broker.directory uses for username_attribute or principal_attribute. Use uid or description. Never wWWHomePage or url on Active Directory: the entry itself can write those whatever the OU's ACL says, so a workload could put another workload's SPIFFE ID on itself (L50). port49d says so at start if you choose one.
    • allow_weak: true acknowledges that a SPIFFE ID is matched by a lookup, not a signature, so the mapping is only as strong as who can write attribute. issuers are the RFC 4514 DNs of the CAs whose certificates it accepts.

    Every workload this verifier accepts then needs exactly one entry, those whose subject names them in identity: included. port49d prints the rule at start.

    Situation The workload sees What to do
    No entry holds its SPIFFE ID refused identity_unmapped add the entry, or the value to it
    Two entries hold it refused identity_ambiguous remove one
    The directory is down past grace refused directory_unavailable, and port49 workload exits 75 restore the directory; pre-warm keeps recently mapped workloads working until then
    The directory is down longer than session.staleness_ceiling live device sessions deny context_stale the same

    Keep pre-warm on: it lets a mapped workload mint through a short directory outage. A workload whose entry changed identity (a host rebuilt with a new directory entry) is released from its pin with port49 directory forget spiffe://example.com/host/backup-01, run through your agent. It needs the forget_principals right and a press of your security key. The login name comes from the subject's username:, else from the entry's username_attribute; the entry needs a unique canonical one either way.

    Who can write the attribute¶

    Whoever can write attribute on an entry decides which workload takes that entry's group memberships. Make it writable only by directory administrators and alert on writes to it: Windows event 5136 or 4662, and on Samba dsdb_json_audit at level 5. port49 prescribes no deny ACL; the measured behavior is in the L50 note for Samba.

    A person's entry is never a workload. An entry that holds a SPIFFE ID in attribute is refused as a person, and the reverse. One window remains: a SPIFFE ID written onto a person's entry takes effect at the next directory refresh, while port49 revoke --principal user:<email> is immediate, so until then the entry could serve both domains. Only a directory administrator can open it, the same person who could add the user to any group. If it happens, revoke the person, then fix the entry (Revocation).

    The directory itself is configured under broker.directory; see The directory.

    Kubernetes service accounts¶

    The pod's projected token is the identity, with no CA to run and no secret at rest. The kubelet writes and rotates the token, and the broker verifies it against the cluster's published keys. The steps are in the Kubernetes guide.

    Unmeasured

    Managed Kubernetes services (GKE, EKS, AKS) are unmeasured: whether their token issuers, discovery and key endpoints behave as the kind cluster did is unknown until they are measured (lab register entry L70, open). The Kubernetes guide is measured on kind only.
