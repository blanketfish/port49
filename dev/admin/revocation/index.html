    Revoking access¶

    Revocation explains what happens and what it cannot do. Below are the commands and how to read the answer. Checking your CA's revocation lists is on Client certificate sign-in.

    What you need¶

    Run port49 login first. Revoking needs the revoke_others right, lifting needs lift_revocations, and every write but --mine needs a press of your security key (Admin access).

    Revoking¶

    You want to stop Run Leaves a standing mark
    a person or workload, everywhere port49 revoke --principal user:alice@example.com yes
    one certificate port49 revoke --cert alice.pem yes
    whoever holds one device login port49 revoke --device leaf1 --username alice no
    one OIDC session port49 revoke --sid <sid> --sid-issuer <issuer> no
    your own sessions port49 revoke --mine no

    On a terminal, --principal asks revoke <principal> everywhere? ... [y/N] first; --yes skips it, and a script with no terminal is not asked. The answer begins with a target: line naming the policy subject the principal belongs to. If it says no subject in the policy in force names it, check the spelling: the mark is written anyway, so a typo of a colleague's address revokes nobody. The spellings are on Identities.

    port49 revoke --list shows what is in force, with each origin (api <who> for an operator, crl <name> or ocsp <responder> for a CA's revocation). A --mine, --device or --sid revocation leaves no mark, so it is not listed; the decision log's revoke record names each, with revocation.by of self, key or a logout. A revocation does not expire, and the agent reconnects with the same key on its own, so only a lift undoes it. Exit codes, and how to read exit 1 and 3: Client commands.

    Name a certificate by file¶

    port49 revoke --cert alice.pem

    It reads the issuer and serial out of the file and prints them before anything is sent:

    port49 revoke: alice.pem: subject "CN=alice,O=Example", issuer "CN=Example Issuing CA,O=Example", serial 0x2a

    The file must hold one certificate, PEM or DER. A file with a private key, more than one certificate (a chain would revoke the CA's serial and say it did) or more than 1 MiB is refused. The by-hand form is --cert-issuer DN --cert-serial HEX, both required, for when you have no file. The issuer must be spelled as Go prints it (RFC 2253); a different spelling matches nothing, and the report says so. The serial is hexadecimal: colons, a 0x and leading zeros are dropped, and digits alone are read as hex, though openssl prints a small serial in decimal first (4096 (0x1000)). The report warns when that may have happened: revoke again with --cert FILE, which sends the serial as explicit hex, then lift the wrong one.

    A certificate revocation closes that certificate's held connections, deletes unspent tokens and marks its live contexts. The principal's other certificates keep working, except that unspent tokens are deleted by (device, username), so they lose theirs on those devices and can mint again. A workload renews under a new serial the mark does not name, so revoke the workload's principal too, and the certificate at your CA so it cannot renew.

    A stolen laptop¶

    1. port49 revoke --principal user:alice@example.com now. It stops every mint, closes the person's held connections and refuses the agent's next request.

    2. Close the device sessions the report names, with the device's own tools. Why TACACS+ cannot do it is on Revocation; Junos says what it does on its own:

      not reached, on a platform that never asks port49 about a command (close these on the device): leaf1 (alice), srx2 (alice)

    3. When your CA has issued the person a new certificate, revoke the old one by --cert (or at the CA) and lift the principal.

    Lifting¶

    port49 revoke --lift --principal user:alice@example.com
port49 revoke --lift --cert alice.pem

    A lift needs lift_revocations and a touch. It restores nothing: contexts the revocation marked stay revoked until a login with a token minted after the lift joins them. On a principal that is not revoked it answers no such revocation is in force.

    A mark whose origin is crl <name> or ocsp <responder> was written because the CA revoked the certificate. The person is told to request a new one, and no lift is offered. --lift --cert is no fix: the next connection checks the CA again and is refused, or, with the list stale, answered certificate_status_unavailable, or admitted under on_unavailable: allow. Lift such a mark only after the CA has unrevoked the certificate. A certificateHold entry is never marked.

    Where marks are kept¶

    A standing mark is in the session store and is read by every broker.

    • A broker on etcd (the normal split) keeps each mark in the store and a copy in broker.state_dir, which puts a mark back after a store restore. Back that directory up (Backup and restore).
    • A single-process port49d on the memory store also writes every mark to broker.revocations_file (The memory store).

    When the file could not be written, the report says NOT saved to broker.revocations_file, port49 revoke exits 3 and port49_revocations_file_failed is 1. Revoke again once the disk is fixed (Revocations file failed).

    Break-glass¶

    Warning

    Offline revocation stops issuance fleet-wide while the brokers are down. Use it only when no admin can reach a running broker.

    Run it with the broker stopped, as the broker's own user. As root it refuses, revokes nothing and names the sudo -u line to use, because the files it writes belong to that user.

    systemctl stop port49-broker              # on every broker host
sudo -u port49-broker port49-broker revoke --offline --principal user:bob@example.com
systemctl start port49-broker

    port49-broker revoke --offline --list shows the marks. It revokes through the store, so etcd must be up, and keeps the copy in broker.state_dir. A port49d that runs its broker in process has port49d revoke --offline, which writes broker.revocations_file.

    docker compose stop port49-broker
docker compose run --rm --no-deps port49-broker revoke --offline --principal user:bob@example.com
docker compose run --rm --no-deps port49-broker revoke --offline --list
docker compose start port49-broker

    --lift instead of the principal's revoke lifts it. port49 store status --metrics 127.0.0.1:9050 reads the broker's stores on the metrics port.

    When no broker is reachable:

    scripts/revoke-offline.sh <ns> <release> -- --principal <name> [--lift|--list]

    It scales the brokers to 0, runs port49-broker revoke --offline against broker-0's volume, and scales back on every exit. The chart is on etcd, which keeps the marks (with a copy in broker.state_dir), so it has no init-revocations step.
